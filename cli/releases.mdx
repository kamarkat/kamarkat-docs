> These commands are for the platform maintainers. They publish the bundle versions every box installs, and you never run them on your own box.

A release ends when the version exists in the registry. **Nothing here touches a
box.** Moving a box onto a published version is that box owner's act, done with
[`kakt promote`](/guides/platform/upgrade-a-box) in their own repository with
their own credentials — or by accepting the upgrade proposal the version raises.

Each command runs from the root of a `kamarkat` checkout (the platform repository) and runs that checkout's own release scripts, so there is one release path. Without an installed `kakt`, use `go run ./cmd/kakt release …` from the checkout.

## kakt release check

Rehearses the next version and checks every component behind its latest release has a reason. Nothing is pushed, so the version stays free.

Because it spends nothing, it chooses a version when you do not: the next
candidate, or the next **patch** when the newest published version is stable. It
says which one it took. Publishing a stable version still requires `--version`,
since that number is consumed.

```bash
kakt release check
```

It runs every packaging step and release gate for the next version. It then lists every component behind its project's newest release today that the component catalog does not explain, and every reason that promised a change in this release which the release does not carry. Each [release page](/versions/lines/0-1) shows those reasons beside red versions, and a version that cannot be explained cannot be documented. It ends with `Ready. <version> can be released.`

## kakt release publish

Publishes a version to the registry.

```bash
kakt release publish --dry-run
kakt release publish
kakt release publish --version 0.1.17-rc.1
kakt release publish --stable --version 0.2.8
```

There are two kinds of version and they are published differently. Without
`--stable` this publishes the next **release candidate**, packaging and pushing
it from the checkout. With `--stable` it publishes a **stable** version the only
way one is ever published: by creating its GitHub release, which is what the
publish workflow runs on.

The steps run in a fixed order:

1. **Decide the version** from the registry: the release candidate after the newest published, unless `--version` names one.
2. **Publish** it: package, run every release gate, write the component inventory, push.

A version is published once. If a step fails after publishing starts, the next
attempt takes the next version.

| Flag | Meaning |
| :- | :- |
| `--stable` | Publish a stable version by creating its GitHub release. Requires `--version` |
| `--dry-run` | Say what each step would do; change nothing |

### Publishing a stable version

```bash
kakt release publish --stable --version 0.2.8
```

`--stable` requires `--version`. A candidate is incremented for you; a stable
version is not, because whether the next one is a patch, a minor or a major says
what the release means — and a version is consumed the moment it is published,
so a guess spends a number meant for something else. Run `kakt release check
--version 0.2.8` first to rehearse it.

**It publishes a commit, not your working tree.** A candidate packages the tree
you have; a stable version is built by the run, from the commit the release
names. So the release names your current commit, and the command refuses a
checkout that is not exactly what the run would build — uncommitted changes are
listed by name, and a commit that is not on the remote is refused because there
would be nothing for the release to point at. This is what keeps the version you
rehearsed and the version you published the same one.

The steps differ from a candidate's only at publication:

1. **Decide** nothing — you named the version.
2. **Check the checkout**: clean, and its commit present on the remote.
3. **Create the release** naming that commit, then **follow the run that
   publishes it**. The command waits, and fails if the run fails. An existing
   release for that version is refused: a version is published once.

Nothing is packaged on your machine. The run builds the charts, the CLI binaries
and their checksums, writes the release body, and updates the Homebrew tap — so a
stable version published any other way would leave the tag, the binaries and the
tap disagreeing with the registry.

If the run fails after the release exists, fix it and re-run that run. Do not
create the release again.

## kakt release docs

Adds published versions to the [release pages](/versions/lines/0-1), and renders every release page.

```bash
kakt release docs 0.1.17-rc.1
kakt release docs
```

For each version named, it records each component's repository link, the newest upstream release on the version's release date, whether the version shipped it, and the catalog's reason when it did not. A version behind with no reason fails, and nothing is written for it. It then renders the release and line pages from every version the docs hold. With no version, it only renders.

| Flag | Meaning |
| :- | :- |
| `--docs-dir` | The docs checkout to write into. Defaults to `../kamarkat-docs` |

## Shared flags

Each is accepted by the commands that read it, and by no others — a command that
does not list a flag has no use for it.

| Flag | Meaning | Accepted by |
| :- | :- | :- |
| `--version` | The version. Defaults to the release candidate after the newest published; required by `publish --stable` | `check`, `publish` |
| `--owner` | The GitHub organisation whose registry the bundle is published to. Defaults to `kamarkat` | `check`, `docs`, `publish` |

`docs` takes the versions it writes as arguments rather than through `--version`.
