> One commit. A removed cluster's name is never used again.

A managed cluster exists because its declaration exists: `registry/clusters/<name>/infrastructure/spokepool.yaml`, the claim your management cluster generates that cluster's Applications from. Remove the file, commit, push — and the management cluster deletes the cluster.

## Before you start

- **The commit is the destruction.** There is no second step and nothing to run afterwards. Once it reaches the branch your management cluster reconciles, the cluster, its nodes and the data on their volumes are gone.
- **Its deployments stop; the applications stay.** The command lists the environment's applications before removing anything — what stops running on this cluster. Their definitions stay in `environments/<env>/` and keep running on every other cluster serving that environment. Removing a cluster never requires editing an application ([Where an app runs](/guides/apps/move-an-app)).
- **Its databases go with it.** Anything you still need must be out before you push.
- **It must not be your burst pool.** The command refuses while the management cluster's `burstSpokePool` names it: the autoscaler adds cloud capacity to that cluster by name, and a name that stops resolving leaves it waiting for a kubeconfig nobody writes. Point it at another cluster or clear it first — in the same commit is fine.
- **Branch protection is doing real work here.** Because the commit destroys a cluster, the branch your management cluster reconciles should require review and the `Cluster removal` check. That check names what the commit destroys, refuses a removal the burst pool still references, refuses one that reaches the management cluster's own declaration, and requires you to state the destruction in the pull request description.

## Step 1: Remove the declaration

From the root of your GitOps repository:

```bash
kakt tenant remove-cluster --mgmt-cluster acme-mgmt-1794447136 --name acme-stg-01
```

It deletes `registry/clusters/acme-stg-01/`, the directory holding the claim. Your working tree is edited; nothing is destroyed, because nothing is committed.

## Step 2: Commit and push — this is the removal

```bash
git add -A registry && git commit -m "Destroy acme-stg-01" && git push
```

Open it as a pull request so the `Cluster removal` check runs, and put the line it asks for in the description:

```
destroy-cluster: acme-stg-01
```

When the commit lands on the reconciled branch, the management cluster stops generating the cluster's Applications, the infrastructure one is deleted with Argo CD's resources-finalizer, the claim goes with it, and Crossplane and Cluster API unwind the cluster.

## Step 3: Watch it finish

The commit returns at once; the cluster takes minutes to go.

```bash
kakt tenant cluster-status --name acme-stg-01 --mgmt-cluster acme-mgmt-1794447136
```

It prints what it observed — the declaration, the two Applications, the claim, the Cluster API object and your provider's inventory — and then the state: `deleting` while the platform is unwinding it, `removed` once your provider reports nothing carrying its ownership label, `failed` if nothing is left that can finish the job. A declaration gone from git is never by itself reported as a destroyed cluster.

<Warning>
This destroys the cluster and everything on it, including its databases. There is no undo.
</Warning>

## When the management cluster is gone

There are no Applications to delete, and nothing on the platform can destroy the cluster. The cluster goes with the box, on the teardown that names it:

```bash
kakt teardown --name acme-mgmt-1794447136 --gitops-dir . --confirm \
  --infrastructure-only acme-mgmt-1794447136,acme-stg-01
```

The named cluster's resources are deleted first, the provider is asked again, and the management cluster goes only once nothing carries the other's ownership label. The run reports the cluster's own cleanup as not performed, and exits non-zero if anything is left — see [Delete a box](/guides/box/delete-a-box).

## What stays behind

- **Secrets.** Each app's secrets are stored under the cluster's name and the app's, and removing the cluster does not delete them. Delete them in your box's secret store once you no longer need them.
- **Backups.** The cluster's database backups stay in your object storage, under a prefix named for the cluster.

## A cluster name is never reused

A cluster's name names more than the cluster: its secret path and its backup prefix are named for it too. A new cluster under a removed name would read the old cluster's secrets, and its databases would find the old backups where theirs must go and refuse to back up at all. Give a replacement a new name. See [Replace a managed cluster](/guides/clusters/replace-a-managed-cluster).
