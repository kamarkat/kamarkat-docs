> The version is the only field your build writes. What was tested is what ships.

## What it is

An application's deployment lives in two repositories, split by the kind of fact each holds.

| Repository | Holds |
| :- | :- |
| **Application repository** | Source code, the chart, and the build that publishes both |
| **GitOps repository** | One directory per application per environment, naming a chart version |

The chart is published to a registry in your own organization, so your applications keep deploying even if Kamarkat' registry is unavailable.

## Getting started

### 1. Build your chart on the platform library

Your chart depends on the `platform-workload` library and declares only what differs:

```yaml
workload:
  component: bff
  image: {repository: <registry>/<app>-bff}
  ports: {http: 3001}
  networkPolicy:
    allowToSameApp: [{app: sdk, port: 3000}]
```

The library renders the service account, service, rollout and network policy, with admission hardening built in. Liveness and readiness use separate paths: liveness never depends on anything outside the process, and readiness reports dependencies.

### 2. Publish from your build

Your build publishes the chart with the image **pinned by digest** inside it, then commits the new version to the application's directory in your GitOps repository. Promoting to the next environment is the same commit with a different target.

### 3. Declare configuration and secrets

Every value your workloads read is declared in your GitOps repository, split by who owns it:

| Kind | Where the value lives |
| :- | :- |
| **Platform credentials**, such as your database or login client | Declared as a capability. You never see or copy the value. |
| **Configuration** | In your values, delivered as a config map |
| **Secrets you choose**, such as a third-party API key | Declared in git, supplied with `soloz fleet secrets` |

A secret's value is never in your repository in any form. Before your workloads start, every declared secret is checked and any missing key is reported by name.

## What you need to know

### Images must be pinned by digest

Admission refuses any image referenced by tag. Because the digest travels inside the chart, there is no field in your GitOps repository where an image could be written.

### Service names are derived by the platform

The gateway routes to a service name derived from your application. An application cannot point a public hostname at another application's service.

### Each application has its own directory

Builds of different applications never contend for one file, and each application syncs, reports health and fails on its own.

### Declared public routes

By default every path is behind login. To serve paths without login, declare them:

```yaml
gateway:
  publicAssets:
    paths: [/manifest.json, /favicon.svg]
  publicRoutes:
    - prefix: /share
      tokenLength: 22
```

Public assets are exact paths, served with GET and HEAD only. Public routes take an unguessable token in the path. No session cookie crosses them in either direction, and the gateway applies safe headers and a rate limit.

### Migrations are yours

The library can run your migration as a pre-sync step. What it migrates is your application's own schema; the platform creates no tables.

## Frequently asked questions

<AccordionGroup>
  <Accordion title="Why do my pods never appear after I add a workload?">
    The workload was probably refused at admission. Every workload needs both `tenant-id` and `app-id` labels and an image pinned by digest. The platform library renders both for you.
  </Accordion>
  <Accordion title="Do I have to supply every secret by hand?">
    Only secrets someone has to choose. Credentials for platform capabilities, and internal tokens that only need to be random, are generated by the platform.
  </Accordion>
</AccordionGroup>
