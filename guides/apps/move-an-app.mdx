> An app runs on every managed cluster that serves its environment. It names no cluster, so there is no placement to change.

This page used to describe editing an app's `clusterName`. That field is gone. A cluster declares the environment it serves, and **every application declared in that environment is deployed to it**:

```
cluster.environmentSlug == the environment directory your app is declared in
```

So an app's deployment set changes when **clusters** change, never when the app does.

## To run an app on another cluster

Declare a cluster that serves its environment. The app deploys to it on the next sync, as an independent instance.

```bash
kakt tenant add-cluster --mgmt-cluster acme-mgmt-1794447136 --name acme-stg-02 \
  --environment stg --provider hetzner --region hel1 --workers 2
```

Nothing under `environments/stg/` is edited, and the app keeps running on every other cluster serving `stg`.

## To stop running it on a cluster

Remove that cluster ([Remove a managed cluster](/guides/clusters/remove-a-managed-cluster)). Its instances go; the app's definition and its instances elsewhere stay. Removing a cluster never requires editing an application.

If you want one app gone from the environment entirely, delete its directory under `environments/<env>/` — that removes it from every cluster serving the environment.

## What each instance owns, and what it does not share

Each deployment is independent. Sharing the definition does not share state:

| Per instance | Shared |
| :- | :- |
| Database, persistent volumes | The application's definition and version |
| Secrets, under that cluster's own `/spoke-pool/<cluster>/` path | What secrets it declares |
| Namespace and in-cluster resources | — |

So `kakt app secrets set` writes the value once per cluster serving the environment, and `kakt app secrets status` reports each deployment separately — a secret supplied on one cluster and absent on another is a real state, not a display artifact.

<Note>
**Public hostnames are the exception, and deliberately so.** A hostname has one owner: two Gateways claiming it would each order a certificate and each publish the same DNS record. So an environment's hostnames are served by one cluster — the only one serving it, or the one declaring `publicIngress: true`. With two or more and no declaration, `kakt app hosts aggregate` refuses rather than choosing.
</Note>

## Relocating data is a different operation

Adding or removing a cluster moves no data. If an app's **data** needs to end up on another cluster, that is a restore, not a declaration change: back up the database on the source cluster, let the new instance provision, restore into it, then retire the old cluster. Nothing in the CLI does that as a side effect of an edit, and nothing here should be read as implying it.
