> Apps first, then the cluster. A retired cluster name is never used again.

Retiring an environment removes its apps, then the managed cluster they ran on. The order matters: an app is removed from its cluster by the box, which needs the cluster to still be there.

## Step 1: Remove its apps

Delete each app's directory in the environment and commit:

```bash
git rm -r environments/stg
git commit -m "Retire stg" && git push
```

The platform removes each app it no longer finds a declaration for, and everything the app ran on its cluster with it. Wait until the apps are gone from the cluster before the next step.

If the cluster also runs apps from another environment, stop here: it is still in use.

## Step 2: Remove the cluster

Removing a cluster's files from your repository does **not** destroy the cluster. The management cluster deliberately never deletes a cluster because its declaration disappeared — a bad merge must not be able to take a cluster down — so retiring one is done by hand on the management cluster.

With the management cluster's kubeconfig, delete the cluster's two Applications, platform first:

```bash
kubectl -n platform-ops delete application acme-stg-01-platform
kubectl -n platform-ops delete application acme-stg-01-infrastructure
```

Deleting `acme-stg-01-infrastructure` destroys the cluster and its nodes. Then remove its declaration so nothing recreates it:

```bash
git rm -r registry/clusters/acme-stg-01 registry/clusters/acme-hub/acme-stg-01-infrastructure.yaml
git commit -m "Remove acme-stg-01" && git push
```

<Warning>
Deleting the `-infrastructure` Application destroys the cluster and everything on it, including its databases. There is no undo. Make sure every app is gone from it first.
</Warning>

## What stays behind

- **Secrets.** An app's secrets are stored in your box's secret store under its cluster and app, and removing the app does not delete them. Delete them in the secret store once you no longer need them.
- **Backups.** The cluster's database backups stay in your object storage, under a prefix named for the cluster.

## The cluster name cannot be reused

A cluster's name names more than the cluster: its secret path and its backup prefix are named for it too. A new cluster under a retired name would read the old cluster's secrets, and its databases would find the old backups where theirs must go and refuse to back up at all. Give a replacement cluster a new name — it can serve the same environment as the one it replaces, and both can run while you verify it. See [Replace a managed cluster](/guides/replace-a-managed-cluster).
