> Kamarkat publishes a version. Your own Renovate proposes it as a pull request, and your control plane applies it once you merge.

## What it is

An upgrade changes the version a cluster pins. Your GitOps repository carries a `renovate.json`. Renovate, running in your own git organization, reads it, watches the bundle chart in `ghcr.io/soloz-io/charts`, and opens a pull request against your repository when a newer version is published.

The pull request changes `targetRevision` and `bundleVersion` in `registry/clusters/<cluster>/bundle.yaml` and nothing else. It carries none of the bundle's content and never writes to your `values.yaml`.

## How it works

<Steps>
  <Step title="A version is published">
    Its release notes record what taking it means.
  </Step>
  <Step title="Your Renovate proposes it">
    The pull request body states what merging and closing it mean. Closing it declines the upgrade.
  </Step>
  <Step title="You merge">
    Nothing changes in a cluster before you merge.
  </Step>
  <Step title="Your control plane reconciles">
    The cluster pulls the bundle chart at the new version and reconciles from it.
  </Step>
</Steps>

### What the release notes tell you

Each release has a **Taking this version** table:

| Field | What it tells you |
| :- | :- |
| **Spans from** | The previous release. |
| **Minimum version this may be taken from** | The oldest version you can upgrade from directly. |
| **Predecessor restorable from this version** | `yes`, `no` or `unknown`: whether reverting the version also restores the cluster's previous state. A release that states nothing reads `unknown`. |

The notes also list security fixes, or say that the version declares none, and list the components that changed.

## What you need to know

### Rollback restores a declaration, not a state

Reverting the version restores what the cluster asks for. It does not undo what the upgrade already did: a controller that migrated stored resources to a new API version leaves them migrated. The **Predecessor restorable** field states, for each release, whether going back restores the previous state.

### Kamarkat holds no access to your repository or clusters

Kamarkat's part ends at publishing a version. The proposal comes from your Renovate, and a cluster changes only when you merge it and your own control plane reconciles the result.

### Proposals depend on your Renovate

If Renovate stops running in your git organization, you stop receiving proposals, and Kamarkat cannot tell. Your box keeps running the versions it pins.

## Frequently asked questions

<AccordionGroup>
  <Accordion title="How do I decline an upgrade?">
    Close the pull request. The cluster stays on the version it pins.
  </Accordion>
  <Accordion title="Can I take a version other than the one proposed?">
    Yes. Set the version on both fields in the cluster's `bundle.yaml` and merge. It must be a published version, at or above the minimum the release notes state.
  </Accordion>
  <Accordion title="Why did my values not change after an upgrade?">
    Upgrades never write to your values. A changed default reaches you through the bundle, unless your values file overrides that field.
  </Accordion>
</AccordionGroup>
