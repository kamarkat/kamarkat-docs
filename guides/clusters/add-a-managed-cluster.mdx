> Day-0 builds a management cluster. A managed cluster is a commit.

Day-0 runs once, to build your box's management cluster. Every managed cluster after that is a declaration in your GitOps repository: you commit it, and the management cluster provisions it. You never run Day-0 again to add one.

## Before you start

- **Choose the name.** It is the cluster's name for its whole life. Applications name the cluster they run on, so a rename is not an edit: it is a new cluster — see [Replace a managed cluster](/guides/clusters/replace-a-managed-cluster) for how one is swapped out. A removed cluster's name cannot be reused (see [Remove a managed cluster](/guides/clusters/remove-a-managed-cluster)).
- **Choose the version.** `--bundle-version` records the platform version this cluster is declared at. Use the version your management cluster runs: what the cluster actually receives is that cluster's platform, because one ArgoCD serves the whole repository.
- **Check the provider supports the environment.** `hybrid` is supported for `dev` only. A `stg` or `prod` cluster runs on `hetzner`. See [Environments](/features/workloads/environments#providers-per-environment).

## Step 1: Declare the cluster

From the root of your GitOps repository:

```bash
kakt tenant add-cluster \
  --mgmt-cluster acme-hub \
  --name acme-stg-01 \
  --environment stg \
  --tenant acme \
  --bundle-version <version> \
  --gitops-repo-url https://github.com/acme-inc/acme-gitops
```

It writes `registry/clusters/acme-stg-01/`, the record of what this cluster is and its claim on your cloud, and two Applications in the management cluster's own directory: `acme-stg-01-infrastructure.yaml`, which creates the cluster, and `acme-stg-01-generated.yaml`, which owns the artifacts the platform writes for it later. Both live there because the management cluster's ArgoCD applies that directory and no other. It refuses a name that is already declared.

<Note>
A managed cluster is a new set of nodes in your cloud account, billed like any other. On `hetzner` it starts with 2 worker nodes unless you pass `--workers`. A `hybrid` cluster buys no cloud workers: it runs on the machines you list in `registry/clusters/<name>/infrastructure/spokepool.yaml`, and has no capacity until you list them.
</Note>

## Step 2: Commit

```bash
git add registry && git commit -m "Declare acme-stg-01" && git push
```

The management cluster provisions the cluster from this commit, then installs the platform on it. It does that from its own boundaries, at the version the management cluster runs — a managed cluster does not pin a platform version of its own.

## Step 3: Verify

```bash
kakt verify --cluster acme-stg-01
```

It waits for the cluster to converge and reports what is outstanding. It reads the cluster's kubeconfig from the box's escrow, using your own `kakt login` session; pass `--kubeconfig` to point elsewhere.
