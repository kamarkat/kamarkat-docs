`kakt tenant scaffold` creates `<org>/<tenant>-gitops` in your git organization and renders it from the platform template. It writes only the facts unique to you: your tenant, that git organization, your domain, region and cluster names. Scaffolding happens once; every change after it is a commit or a pull request.

## Step 1: Preview what you will receive

A dry run renders the repository locally and creates nothing:

```bash
kakt tenant scaffold \
  --tenant acme \
  --box acme-inc \
  --domain acme.example \
  --region hel1 \
  --platform-admin <your-infisical-id> \
  --dry-run
```

<Note>
`--platform-admin` is the one human this box accepts for escrow-backed operations, by Infisical's account id — the `identity` value from [Get started, Step 1](/quickstart/get-started#step-1-sign-in-and-create-your-escrow-account), or `kakt whoami` again. Omit it and the box authorizes no human session at all: every escrow command refuses until you declare one. See [Platform administrator and access](/documentation/escrow/platform-administrator).
</Note>

| Flag | Meaning |
| :- | :- |
| `--tenant` | Your tenant identifier, lower-case. It names the repository and your box. |
| `--box` | The git organization the repository is created in — `github.com/<box>/<tenant>-gitops`. Not the box's name; that is `--box-id`. |
| `--domain` | Your base domain. |
| `--platform-admin` | Infisical's account id for the one human this box accepts for escrow-backed operations. `kakt whoami` prints yours. |
| `--subdomain` | Optional. A DNS label every hostname sits under; empty publishes on the apex. |
| `--provider` | `hetzner` (default), or `hybrid` for nodes on your own machines. |
| `--region` | The cloud region your clusters run in. |
| `--workers` | Cloud worker nodes the box starts with. Defaults to 2. |
| `--cluster` | The management cluster's name. Defaults to `<tenant>-hub`. |
| `--bundle-version` | The platform version the box starts on. A released CLI defaults to the version it carries; an unreleased build refuses rather than guess. |

## Step 2: Scaffold and store your credentials

Run the same command without `--dry-run`, from a shell where you exported your [credentials](/quickstart/prerequisites#step-3-gather-your-credentials):

```bash
kakt tenant scaffold \
  --tenant acme \
  --box acme-inc \
  --domain acme.example \
  --region hel1 \
  --platform-admin <your-infisical-id> \
  --escrow-url "$INFISICAL_ESCROW_URL" \
  --escrow-project-id "$INFISICAL_ESCROW_PROJECT_ID" \
  --escrow-client-id "$INFISICAL_ESCROW_CLIENT_ID" \
  --escrow-client-secret "$INFISICAL_ESCROW_CLIENT_SECRET"
```

The scaffold then:

1. Creates and pushes `acme-inc/acme-gitops`.
2. Prompts for any of `HCLOUD_TOKEN`, `GITOPS_TOKEN` or `TS_AUTHKEY` you did not supply, with echo disabled.
3. Verifies the escrow, and refuses if a capability your box selects has no credential.
4. Stores every credential as a secret on the new repository.
5. Starts the **Bootstrap cluster** workflow on it.

```text
[scaffold] created acme-inc/acme-gitops
[scaffold] pushed to https://github.com/acme-inc/acme-gitops
[scaffold] bootstrap dispatched on acme-inc/acme-gitops
  https://github.com/acme-inc/acme-gitops/actions/workflows/bootstrap-cluster.yml
```

<Note>
If a credential is missing, the scaffold creates the repository and prints the exact `gh secret set` commands to finish, followed by the command that starts Day-0. Nothing runs until they are set.
</Note>

## What is in your repository

```text
acme-gitops/
├── registry/clusters/<cluster>/   one directory per cluster: bundle.yaml (version), values.yaml (yours)
├── environments/<env>/<app>/      one directory per application, added in "Run your first app"
├── templates/                     what you copy to add a cluster, an app or a workload
└── renovate.json                  proposes new platform versions as pull requests
```

Two workflows come with it. **Bundle pre-flight** judges an upgrade proposal against the cluster it targets. **Cluster removal** reviews a commit that removes a managed cluster's declaration — which is what destroys that cluster — so the branch your management cluster reconciles should require review and that check.

The platform version in `bundle.yaml` changes only through upgrade proposals. Its `repoURL` names the registry the platform's charts are pulled from, and changes if that registry moves. `values.yaml` holds only what you change from the defaults.
