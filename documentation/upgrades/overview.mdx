> Kamarkat publishes a version. Your cluster declares which one it runs. Those are two separate acts, and the second is yours.

The platform is distributed as one versioned artifact — the **bundle**. A cluster consumes it by naming a version and supplying its own values, so what a cluster runs is a line in your repository rather than something applied to it from outside.

## What an upgrade is

Changing the bundle version a cluster declares. That is the whole operation: the declaration changes, your management cluster reconciles the new version, and the cluster converges on it.

What an upgrade is **not**:

- It is not content arriving in your repository. The change is a version, and the bundle's content stays where it is published.
- It is not a write to your `values.yaml`. Values are yours; defaults belong to the chart.
- It is not a component bump. The bundle moves as one artifact, and components are declared once inside it.
- It is not something the platform performs. The platform publishes and may propose; it holds no credential that changes anything running in your box.

## Who does what

| | Platform | You |
|---|---|---|
| Publish a bundle version | ✅ | |
| Record what taking it means — the versions it spans, its security fixes, its declared minimum, whether it is reversible | ✅ | |
| Decide which clusters take it, and when | | ✅ |
| Change the version a cluster declares | | ✅ |
| Reconcile the change | | your management cluster |
