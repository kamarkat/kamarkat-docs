> Going back restores what the cluster asks for. It does not always restore what the upgrade already did.

## Before you start

Read the release notes of the version you are leaving: the release for tag `v<version>` on `kamarkat/kamarkat`. The **Predecessor restorable from this version** row of its **Taking this version** table says whether reverting restores the previous state:

| Value | Meaning |
| :- | :- |
| `yes` | Going back restores the cluster's previous state. |
| `no` | The upgrade changed something going back does not undo — a controller that migrated stored resources to a new API version leaves them migrated. Going back may leave the cluster unable to reconcile. |
| `unknown` | Reversibility was not declared for this release, which is the default. Treat it as `no`. |

## Step 1: Revert the version

Revert the commit that upgraded the cluster:

```bash
git revert <commit> && git push
```

That is the whole rollback: the commit moved every reference the version appears
in, so reverting it moves them all back together.

Where there is no single commit to revert, name the version instead and let the
command find every reference:

```bash
kakt release promote --version <the version it ran before>
```

## Step 2: Verify

The push rolls the cluster back the same way it rolled forward: your control
plane reconciles it, and the **Bundle sync** workflow confirms the cluster
reached the version. Without a `KUBECONFIG_<cluster>` secret it confirms
nothing, and you check it yourself:

```bash
kakt verify --cluster acme-mgmt-1794447136
```

If the cluster does not converge on the previous version, go forward instead: a later version that fixes the problem is the way out of a `no`.
