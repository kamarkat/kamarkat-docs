> Software agents are participants in your platform, not an independent control plane.

Running software agents in production requires more than an LLM API key. Real agentic workflows write files, run tools, call specialists, and retain memory across multi-turn interactions. Without a platform foundation, engineering teams assemble brittle custom scaffolding: unmanaged container runners, manual storage synchronization, and loose credential exposure.

Kamarkat provides a native execution runtime for agentic workloads directly inside your cloud infrastructure. You declare agent definitions, system instructions, and tools as versioned content; your platform provisions isolated sandboxes, manages turn-by-turn workspace persistence, and coordinates cross-agent collaboration over open protocols.

## What this solves

Building custom infrastructure for software agents introduces four operational failures:

- **State loss across turns**: Containers restart, scale down, or crash between turns. Scratch files, compiled artifacts, and tool outputs disappear unless teams build custom persistence hooks into application logic.
- **Credential leakage into sandboxes**: Granting agents direct access to cloud object storage or databases risks accidental credential exfiltration through model execution or third-party tools.
- **Fragmented delivery and runtime forks**: When each agent product writes its own serving endpoints, Dockerfiles, and deployment scripts, runtime fixes and prompt improvements fragment across multiple repositories.
- **Unmanaged agent-to-agent communication**: As agents multiply, they need to request data from specialists across different applications without ad-hoc HTTP endpoints, custom polling, or unauthenticated backchannels.

Kamarkat resolves these challenges by making agent execution a native platform capability, governed by the same declarative contracts that manage your applications and clusters.

## Three platform invariants

The agentic layer adheres strictly to three architectural boundaries:

1. **Declarative desired state remains authoritative**: Agents read platform state and propose changes through version control declarations. Agents never bypass GitOps to mutate cloud infrastructure directly.
2. **Agent content is separated from the serving runtime**: An agent pack is pure data—declarations, prompt fragments, tools, and skills. The platform ships and maintains the serving runtime and execution engine.
3. **Business ownership and credential containment**: Sandboxes execute on your managed clusters. Workload containers never receive cloud provider or object storage credentials; platform sidecars mediate storage and egress.

1. **You author an agent pack**: You organize agent topologies, prompts, and tools into a standardized pack directory and commit it to your repository.
2. **Standing pack servers serve the catalog**: A standing, stateless pack server inside the cluster runs continuously to serve definitions, agent DAGs, and tool binaries. They do not run user code or hold user sessions.
3. **Sandboxes provision strictly on demand**: Attaching a pack in the UI attaches its badge without consuming cluster compute. When you submit your prompt, the platform provisions an isolated Sandbox Pod, mounts your persistent workspace, pulls tools from the pack server, and executes the turn.
4. **Platform sidecars persist workspace state**: As agents execute turns, native sidecars capture file changes to your object storage and provide zero-downtime atomic refreshes for shared workspaces.
5. **Idle sandboxes clean up and resurrect transparently**: After 15 minutes of inactivity, the platform terminates the pod after a teardown checkpoint. Sending a new message later spins up a fresh sandbox and mounts your persistent workspace right back up.
6. **The platform routes agent collaboration**: When agents need capabilities from another pack, the platform coordinates requests over the open A2A protocol.
