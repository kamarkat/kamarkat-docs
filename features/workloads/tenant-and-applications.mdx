> Being in the same tenant never grants access. Only a declaration does.

## What it is

Kamarkat names two things separately:

| | `tenantId` | `appId` |
| :- | :- | :- |
| **Names** | The tenant that owns the box | A product running on it |
| **Identity** | An organization in the identity provider | A project within that organization |
| **Namespace** | — | `tenant-<tenantId>-<appId>` |
| **Repository** | One per box, named when the box is created | One directory per application |
| **Cost attribution** | `tenant-id` label | `app-id` label |

For example, a tenant `acme` running two products, `web` and `agents`, gets the namespaces `tenant-acme-web` and `tenant-acme-agents`. Both are attributed to `acme`, and costs split by product.

A tenant may hold several clusters. Each has its own name (`clusterName`), which never stands in for the tenant.

<Note>
**Organization** means one thing only: the identity provider's own container for users, projects and clients. Your tenant is bound to one. Everywhere else — the box, its clusters, its applications, its costs — the platform's word is **tenant**.
</Note>

## Applications are isolated by default

Each application gets its own namespace, service account, network policy, logical database and secret path. Network traffic is **default-deny**. Two applications of one tenant are as separated from each other as if they belonged to different customers.

## Connecting applications

### Calling another application's service

An application declares the workloads it calls. From one entry the platform renders both the network rule and the URL the caller uses:

```yaml
dependsOn:
  - app: agents
    workload: agents-serve
    port: 3005
    urlEnv: [AGENTS_URL]
```

You never write a namespace. It is derived from the tenant and application, so a rename moves both ends of the call together.

### Calling another application's API

When one application calls another's authenticated API, **both sides declare it**:

```yaml
# caller
identity:
  backendDependencies: [web]
# target
identity:
  allowedConsumers: [agents]
```

The platform renders the network rules in both directions and the token audience the caller needs. A build fails if only one side declares.

### Sharing data

Data follows the application. To let one application read another's data, the owner names its readers:

```yaml
sharedData:
  - name: user-directory
    owner: web
    readers: [agents]
```

The owner keeps the database; each reader is granted a role on it.

## What you need to know

### There is no cross-tenant traffic

A box belongs to one tenant, so another tenant is another box — in another cloud account, with no shared management cluster. There is also no field in which an application could name one. The isolation that matters on your box is therefore between your own applications, which is what the rest of this page describes.

### A missing declaration hangs rather than failing

Denied traffic is dropped silently. If a call hangs, check that both sides have declared the dependency.

### Identity is bound to an immutable key

Renaming your tenant never creates a second organization in the identity provider. The binding between your tenant and its organization there is recorded once, against an immutable key, and never inferred from a name.

## Frequently asked questions

<AccordionGroup>
  <Accordion title="Can two applications share one database?">
    No. One application owns each database. Others can be granted read access through `sharedData`, so a schema migration is never a negotiation between two release cycles.
  </Accordion>
  <Accordion title="Can I reach another tenant's application?">
    No. There is no field in which another tenant could be named.
  </Accordion>
