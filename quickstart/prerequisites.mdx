Everything below belongs to you. Kamarkat never receives any of it: the credentials are stored as secrets on your own GitOps repository and used only by your own CI.

## Step 1: Prepare your accounts

| Account | What it is for |
| :- | :- |
| **Cloud account** | Where your clusters run, and what you are billed for. The `hetzner` provider is the default. |
| **Git organization** | Holds your GitOps repository and your application repositories, runs Day-0 in its CI, and hosts your application charts and images in its package registry. |
| **Domain** | Every hostname in your box sits under it. Its DNS zone must be hosted with your cloud provider's DNS service, because the box creates records and proves domain ownership there for its certificates. |
| **Escrow secret manager** | Holds your box's master keys and admin credential outside the box. See [Get started](/quickstart/get-started). |
| **Object storage** (recommended) | Destination for database backups. A production box without it has no backups. |

## Step 2: Install the tools

You need `git`, `kubectl` and the GitHub CLI `gh`, plus the `kakt` CLI.

The `kakt` binary is published with each platform release. Install it with
Homebrew:

```bash
brew install kamarkat/tap/kakt
kakt bundle-version
```

Without Homebrew, the installer detects your operating system and architecture,
verifies the download against the checksum the release publishes, and installs
to a directory you own:

```bash
curl -fsSL https://raw.githubusercontent.com/kamarkat/kamarkat/main/scripts/install.sh | sh
```

Pass `--version 0.2.7` to install a specific one, or `--bin-dir` to choose where
it goes. To read the script before running it, open that URL first.

`kakt bundle-version` prints the platform version the binary carries.

You sign in with it on the next page: `kakt login` opens your escrow secret manager in the browser, where you create the account if you do not have one. It is how every command that reaches an escrow authenticates, and the only credential you keep on your own machine.

<Note>
**Installing by hand instead.** Each release publishes `kakt-linux-amd64`, `kakt-linux-arm64`, `kakt-darwin-amd64` and `kakt-darwin-arm64`, with a `SHA256SUMS` file to check them against:

```bash
export KAKT_VERSION=<version>
base="https://github.com/kamarkat/kamarkat/releases/download/v${KAKT_VERSION}"
curl -fsSL -O "${base}/kakt-linux-amd64" -O "${base}/SHA256SUMS"
shasum -a 256 -c SHA256SUMS --ignore-missing
chmod +x kakt-linux-amd64 && sudo mv kakt-linux-amd64 /usr/local/bin/kakt
```

**Do not build it with `go install`.** The version a release carries is injected at build time, so a build from source reports `development` — and a `development` binary reads platform content from your working directory rather than from itself, and creates a box that carries no bootstrap workflow. Use a published binary.
</Note>

## Step 3: Gather your credentials

Day-0 runs under secrets your box keeps in its escrow. Five values are the exception and live on the GitOps repository: the four that say where that escrow is, and the git token, because your own application builds read it too and GitHub is where they look. [`kakt box init`](/quickstart/initialize-a-box) collects them for you — one step each, opening the page that issues the credential and waiting while you create it — and stores them on the repository it creates. So this is what to expect to be asked for, not a list to assemble in advance.

One exception is worth doing first, because it is needed before the repository exists.

### Before you create the box

| Credential | What it is |
| :- | :- |
| `GITHUB_ORG_SETUP_TOKEN` | **Yours, not the box's.** The credential that creates the repository in your git organization, so it is needed before any repository secret can be set. Either an App installation token, which is preferred because the access stays yours to revoke, or a personal access token with the `repo` **and `workflow`** scopes — supply whichever you have and nothing else changes. `workflow` is not implied by `repo`, and your box's repository carries the workflow that bootstraps it, so a token without it creates the repository and is then refused by the push. `kakt box init` asks for it and keeps it on this machine, so you supply it once per machine rather than once per box. |

### Required

| Secret | What it is |
| :- | :- |
| `HCLOUD_TOKEN` | Your cloud API token, read and write. Your clusters are created with it. `kakt box init` escrows it, and every command that creates or destroys infrastructure reads it from there — so you supply it once, and never as a repository secret. |
| `GITOPS_REPO_WRITE_TOKEN` | Write access to your git organization's repositories, plus that organization's **Secrets: write** permission. Day-0 commits what it generates with it, and your application builds inherit it. |
| `ESCROW_PROVIDER_URL`, `ESCROW_PROVIDER_PROJECT_ID`, `ESCROW_PROVIDER_CLIENT_ID`, `ESCROW_PROVIDER_CLIENT_SECRET` | Your escrow. You create these on the [next page](/quickstart/get-started) — nothing to gather in advance. `kakt box init` refuses without them, because an escrow cannot be added after the fact. |

### Required for what your box runs

`kakt box init` refuses if a capability your box selects has no credential.

| Secret | What it is for |
| :- | :- |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | Backups of the platform database — an object-storage key for the region your box runs in. Escrowed, not stored on the repository. |
| `GHCR_USERNAME`, `GHCR_TOKEN` | Pulling your own private images **and your own private chart packages**. The platform's images are public. The token needs the `read:packages` scope, which neither `repo` nor `workflow` implies — without it your application's pods report `ImagePullBackOff` with a `401` from the registry's token endpoint, and a chart published to your organization fails to download with `403: denied`. A package your organization published after the token was issued is also refused until the package grants that token's owner read access. Escrowed, not stored on the repository. |

### Handled for you, and not stored here

Your box runs its own secret store, separate from your escrow, and it has an
administrator account. You are never asked for it and there is no repository
secret to set.

`kakt box init` creates that account for the address you signed in with, with a
generated password, and writes both to your escrow. Every bootstrap — including
a re-run, and a rebuild after you lose a management cluster — reads that same
credential back from the escrow, which is what lets a second run re-enter a
secret store the first one created.

It is kept only in your escrow because a repository secret cannot be read back:
a second copy there could drift from the real one with nothing able to detect it.
`kakt escrow verify` reports what your escrow holds.

### Optional

| Secret | What it is for |
| :- | :- |
| `GRAFANA_IRM_ALERTMANAGER_URL`, `GRAFANA_IRM_HEARTBEAT_URL` | Where the management cluster's critical and warning alerts page you, and a heartbeat that pages when it stops reporting. These are the hub's: a managed cluster emails its own alerts and is watched by the hub, so you supply these once and nothing per cluster. Metrics, logs and dashboards run in the box without them. |
| `IDENTITY_PROVIDER_SMTP_URL` | Outbound mail for identity messages and alert email. |
| `TS_AUTHKEY` | Only if a managed cluster of this box accepts nodes on your own premises, which join over your tailnet. |

All of these are escrowed too. Only the five above are repository secrets.

### Where each one ends up

Worth being exact about, because it decides what a rebuilt box can still reach.

| Kept on the repository | Kept in the escrow |
| :- | :- |
| `ESCROW_PROVIDER_URL`, `ESCROW_PROVIDER_PROJECT_ID`, `ESCROW_PROVIDER_CLIENT_ID`, `ESCROW_PROVIDER_CLIENT_SECRET` — where the escrow is. CI has to know this much before it can read anything else | everything else your box runs on: the cloud token, the object-storage key, your registry credential, the alert destinations, outbound mail, the tailnet key |
| `GITOPS_REPO_WRITE_TOKEN` — your application builds read it from your organization, and they cannot read an escrow | |

A repository secret cannot be read back once set, so a copy there is a copy nothing
can compare — which is why these moved. The escrow is also the only place that
still answers when the management cluster is gone, or does not exist yet.

<Tip>
Export each value as an environment variable of the same name in the shell you will run `kakt box init` in. It reads them from there and stores them on your repository. It never prints or keeps them.
</Tip>
