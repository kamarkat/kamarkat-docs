> These commands create a box and the clusters in it, confirm they converged, and destroy them. Everything they write lands in your GitOps repository or your own cloud account.

## Create

### kakt box init

Collects the credentials a box is built with, before anything exists to hold them. Each one that is missing gets a numbered step: what it is for, the page that issues it, the browser opened on that page, and a prompt that waits while you create it.

```bash
kakt box init
```

| Flag | Meaning |
| :- | :- |
| `--provider` | Which credentials this box needs: `hetzner` (default), or `hybrid`, which also needs a tailnet key |
| `--private-registry` | This box runs your own private images, which needs a registry credential |
| `--no-browser` | Print the address of each page instead of opening it. Also `KAKT_NO_BROWSER` |

Values are read without echo and staged under `~/.kamarkat/` with mode `0600`, and the same run then creates the box with them. Re-running is normal: anything already present is skipped, and an answer left empty is reported as outstanding — in which case **nothing is created** and the next run asks only for what is missing. In automation, set the variables and pass `--no-prompt`.

It does not create the escrow, which is [`kakt escrow init`](/cli/escrow-and-encryption#kakt-escrow-init), and it never asks for the box Infisical administrator, which is generated and escrowed when the management cluster is declared. See [Create your box](/quickstart/create-your-box).

Once the credential set is complete, the same command creates `<box>/<tenant>-gitops`, renders it from the platform template **with no clusters**, and stores your credentials on it as repository secrets.

```bash
kakt box init \
  --tenant acme \
  --box acme-inc \
  --domain acme.example \
  --region hel1
```

<Note>
**The management hub takes no `--environment`.** It is environment-independent: it
has its own identity (`boxId`), its own secret scope
(`management.infisicalEnvironmentSlug`) and its own capacity policy. A `dev`, `stg`
or `prod` stage is a property of each **workload** cluster, declared with
`kakt tenant add-cluster --environment`, and one hub manages clusters in all of
them.

The hub's secret scope is created for the box during bootstrap, so there is
nothing to set up in Infisical beforehand.
</Note>

Creating a box happens once. Every change after it is a commit or a pull request. See [Create your box](/quickstart/create-your-box) for the credentials it expects and what the repository contains.

| Flag | Meaning |
| :- | :- |
| `--tenant` | Your tenant identifier, lower-case. Required. It names the repository and your box |
| `--box` | The git organization the repository is created in — `github.com/<box>/<tenant>-gitops`. Required. It is **not** the box's name: that is `--box-id` |
| `--domain` | Your base domain. Required |
| `--platform-admin` | The one human this box accepts for escrow-backed operations, by Infisical's account id. Defaults to the signed-in session; pass it only to name somebody else |
| `--subdomain` | A DNS label every hostname sits under; empty publishes on the apex |
| `--provider` | `hetzner` (default), or `hybrid` for nodes on your own machines |
| `--region` | The cloud region your clusters run in. Defaults to `hel1` |
| `--box-id` | The box's own permanent identity, **pinned forever**. Defaults to `<tenant>-hub`, which is also the name its first management cluster usually takes. Different from `--box` above |
| `--workers` | Cloud worker nodes a cluster of this box starts with. Defaults to 2. Pass `0` to run on nodes on your own premises alone, which then have to be there |
| `--private` | Create the repository private. Default `true` |
| `--private-registry` | Your applications run private images, which makes a registry credential required |
| `--bundle-version` | The platform version the box starts on. A released CLI defaults to the version it carries; an unreleased build has none and refuses rather than guess. `development` reads charts from your current branch |
| `--dry-run` | Render only; create and push nothing |
| `--out` | The checkout to leave behind. Defaults to `./<tenant>-gitops`, and the next command runs inside it |
| `--no-prompt` | Never prompt: every credential comes from the environment or `~/.kamarkat/`, and a missing one stops the run before anything is created |
| `--no-browser` | Do not open the page that issues each credential; print the address instead. Also `KAKT_NO_BROWSER` |

<Warning>
**`--box` and `--box-id` are different values.** `--box` is your git organization — where the repository is created. `--box-id` is the box's permanent identity, which keys its escrow path and its DNS records. For `acme-inc/acme-gitops` holding a box called `acme-hub`, that is `--box acme-inc --box-id acme-hub`. One org can hold several boxes.
</Warning>

<Note>
**Credentials are collected one step at a time.** Anything missing is asked for in a numbered step that opens the page issuing it and waits while you create it; input is never echoed, and what is already in your environment or kept in `~/.kamarkat/` is skipped. Two are not asked for at all: the box Infisical administrator's address comes from your session, and its password is generated and escrowed. [Prerequisites](/quickstart/prerequisites#step-3-gather-your-credentials) lists what to expect.
</Note>

<Warning>
**The administrator comes from your session.** `kakt login` first, and the box is declared with your account id — printed as it is used. Creating a box with no session renders a repository that declares none, and a box that declares none authorizes **no** human session until one is added. [Platform administrator and access](/documentation/escrow/platform-administrator) explains why it is an account id rather than an address.
</Warning>

<Warning>
`--box-id` is chosen once and never changes. Your escrow is keyed by it, so every escrow command takes the same value — and a box that is rebuilt keeps it, which is how the new management cluster finds the old one's keys. Leave it unset unless you have a reason, and record what it resolved to.
</Warning>

<Note>
`--private` interacts with your git plan. On GitHub's free plan, git organization secrets reach public repositories only, so a private repository's builds receive an empty credential. [Deploy your app](/quickstart/deploy-your-app#step-1-give-your-builds-write-access-to-the-gitops-repository) covers the per-repository alternative.
</Note>

### kakt tenant add-cluster

Declares an additional managed cluster. It renders the cluster template your GitOps repository carries; the management cluster provisions the cluster from your commit. No Day-0 run is involved. For the whole task, see [Add a managed cluster](/guides/clusters/add-a-managed-cluster).

```bash
kakt tenant add-cluster \
  --mgmt-cluster acme-hub \
  --name acme-02 \
  --tenant acme \
  --bundle-version <version> \
  --gitops-repo-url https://github.com/acme-inc/acme-gitops
```

| Flag | Meaning |
| :- | :- |
| `--mgmt-cluster` | The management cluster that creates this one. Required |
| `--name` | The managed cluster's name, and what applications name to run on it. Required |
| `--tenant` | The tenant that owns it. Required |
| `--bundle-version` | The platform version this cluster is declared at, recorded in its values file. Required. A managed cluster receives the management cluster's platform, so this does not pin one of its own |
| `--gitops-repo-url` | Your GitOps repository's URL. Required |
| `--provider`, `--region` | Where and what it is, if it differs from the defaults |
| `--environment` | The stage this cluster serves. Several clusters may serve one stage, which is how a replacement runs beside the cluster it replaces |
| `--workers` | Cloud worker nodes it starts with. Defaults to 2 on `hetzner` |
| `--public-tls-issuer` | The ACME issuer for public certificates. Defaults to `letsencrypt-prod` |
| `--gitops-dir` | Your GitOps repository. Defaults to the current directory |

<Note>
`--bundle-version` on `bootstrap-mgmt` must already be published, in the registry your `bundle.yaml` files pull from, and pullable without credentials: the box cannot converge on a version its registry does not hold. On `add-cluster` it is a record, since the managed cluster runs the management cluster's platform.
</Note>

<Warning>
`--name` is the cluster's name for its whole life. Applications name the cluster they run on, and its secret path and backup prefix are named for it, so renaming it later is not an edit — it is a new cluster.
</Warning>

### kakt tenant set-gitops-token

Publishes the credential your application builds use to pin a chart version. Creating the box does this already; re-run it when the token used then lacked your git organization's **Secrets: write** permission.

```bash
kakt tenant set-gitops-token --org acme-inc
```

The token is read from stdin when `--token` is omitted, which keeps it out of your shell history. `--repo owner/name` publishes on one repository instead of the whole git organization, and `--discover --gitops-repo acme-inc/acme-gitops` finds the repositories whose workflows write to it.

### kakt tenant add-management

Declares a management cluster for the box this repository is — **its first, or a
replacement for the one it has.** A box outlives its clusters: the box keeps its
`boxId` and the management cluster's own name changes, because that name keys the
cluster's objects, its nodes and its database's WAL archive prefix.

```bash
kakt tenant add-management --name acme-hub          # the box's first
kakt tenant add-management --name acme-mgmt-02      # its replacement
```

| Flag | Meaning |
| --- | --- |
| `--name` | The cluster's name. Required. For a replacement, never a name this box has used |
| `--from` | The cluster this one succeeds. Needed only when the box already declares more than one, and meaningless for a first cluster |
| `--gitops-dir` | The box's repository. Defaults to the working directory |
| `--provider`, `--region`, `--bundle-version`, `--workers` | What this cluster differs from its box in. Each defaults to what `registry/box.yaml` declares |

The box is not a flag. It is read from `registry/box.yaml` in the repository you
run this in, because `boxId` is already written there and a mistyped one does not
fail — it addresses another box's escrow, or claims another box's DNS records. A
directory that declares no box says so.

**The first cluster** is rendered from `templates/mgmt` using what the box
declared: your domain, your escrow, your provider and region. It is also the
moment this box's own Infisical administrator is created — the password is
generated, written to your escrow, and set on the repository, and a later run
reads the escrowed one back rather than minting a second over the live instance.

**A replacement** is rendered from the management cluster already declared here,
so it inherits this box's domain, provider, region and escrow coordinates along
with every later edit. Day-0's output is not carried over: `generated/` holds the
previous cluster's CAPI Cluster, its PKI and its load balancer address, and the
new cluster's Day-0 writes its own.

Committing declares it. Create it by dispatching the repository's own workflow
with the new name:

```bash
gh workflow run bootstrap-cluster -f cluster=acme-mgmt-02
```

Both declarations can exist at once, which is what makes a replacement
reversible: the predecessor keeps serving and stays demotable until the
switchover. Declaring is not building — the bootstrap refuses a second cluster
while the first still owns infrastructure, which is the invariant below.

### One management cluster at a time

A box has at most one management cluster holding infrastructure. It may have had
several over its life — that is what `boxId` is for — but two at once are two
control planes reconciling the same repository, each provisioning the other's
workload clusters under names already taken.

`bootstrap` establishes this before it provisions anything, and it asks the
**provider**, not Kubernetes and not this repository. A declaration here outlives
every cluster by design, an escrow artefact is kept deliberately, and an
unreachable Kubernetes API is also what a wedged cluster with running servers
looks like. Provider resources carry their owning cluster's name as a label, so
they answer without a kubeconfig:

```text
Cannot create the management cluster.

Box: acme-hub
Creating: acme-mgmt-02

This box already has a management cluster:

  acme-hub still owns 7 provider resource(s)

A box has one management cluster at a time. Two of them reconcile the same
declarations in this repository, so each would provision the other's workload
clusters under names already taken.

Destroy it:
  kakt teardown --name acme-hub --gitops-dir . --confirm

Nothing here needs deleting by hand, and nothing is lost by this refusal:
this repository is reused as it is, boxId stays acme-hub, and the escrow
artefacts and database archives of every past incarnation stay under their
own names.
```

Three things follow from asking the provider:

- A cluster you destroyed is **verifiably** gone — it owns no labelled resource —
  so a new incarnation is admitted immediately. You never delete this repository.
- A failed attempt at the *same* cluster is a retry, not a duplicate. The run
  reports what it is resuming.
- An inventory that cannot be read is refused rather than read as empty, because
  an unreadable answer is the same evidence as an unasked question.

Workload clusters are included: a replacement is refused while any workload
cluster this box declares still owns provider resources. The management cluster
goes last, so build the replacement first and those clusters are left unmanaged
and still billing — then rebuilt from the claims still committed here.

Two further properties, because a check alone is not a guarantee:

- **A removed declaration does not hide a cluster.** The names asked about come from
  what this repository declares *and* from every management cluster its history
  shows was ever declared. Delete a cluster's directory while its servers are
  running and it is still asked about, because the provider's label identifies a
  cluster and only the box's own records can enumerate its clusters.
- **One bootstrap at a time per box.** `bootstrap-cluster` is serialized on the
  repository, so two overlapping dispatches cannot both read an empty inventory and
  both build. A second dispatch of the same cluster waits and resumes; a different
  one waits and is then refused.

A record that cannot be read — an unreadable inventory, a directory that is not a
repository — is refused rather than read as "nothing there".

### Replacing a management cluster

```bash
# 1. remove the workload clusters, which is a commit each
kakt tenant remove-cluster --mgmt-cluster acme-hub --name acme-stg-01

# 2. destroy the current management cluster
kakt teardown --name acme-hub --gitops-dir . --confirm

# 3. declare the replacement; boxId is untouched
kakt tenant add-management --name acme-mgmt-02

# 4. build it
gh workflow run bootstrap-cluster -f cluster=acme-mgmt-02
```

The repository, the box's identity, its escrow scope and every past incarnation's
backups are preserved throughout. Application declarations under
`environments/` belong to the environment, not to the cluster, so they are
untouched by a replacement.

## Day-0, one step at a time

Day-0 runs as a workflow in your GitOps repository and calls these for you. Run them directly only when you are working on a box deliberately.

### kakt bootstrap-mgmt

Creates the management cluster and stops there. The gates that decide whether the box is usable — secrets present, the secret store reachable, databases provisioned, declared managed clusters actually up — are separate steps.

```bash
kakt bootstrap-mgmt --name acme-hub --provider hetzner --region hel1
```

<Warning>
This gives you a reconciled management cluster and no assurance about anything else. A box is bootstrapped when Day-0 has run every step in order, not when this command exits.
</Warning>

Notable flags: `--workers` (pass `0` to run on your own premises alone), `--on-prem` with `--tailnet-name` to accept nodes that join over your tailnet, `--oidc-issuer-url` with `--oidc-client-id` to name the identity provider the API server accepts tokens from, `--dry-run` to validate prerequisites and render manifests without provisioning, and `--gating` to choose whether boundaries activate in phase order or reconcile concurrently.

### kakt init-secrets

Generates the bootstrap secrets the secret store starts from, and creates the machine identity the platform authenticates with afterwards. Aliased as `kakt bootstrap-secrets`.

```bash
kakt init-secrets
```

### kakt configure-github-access

Gives the GitOps engine access to your repositories, and supplies the pull credential for your private images. It runs before `init-secrets`, because the GitOps engine creates the namespaces that step writes into.

```bash
kakt configure-github-access --org-url https://github.com/acme-inc
```

### kakt configure-tailscale

Supplies the auth key and hostname a control plane uses to join your tailnet, for boxes that accept nodes on your own premises. It runs before a managed cluster is provisioned on that path.

```bash
kakt configure-tailscale
```

Values default to `~/.kamarkat/tailscale/authkey` and `~/.kamarkat/tailscale/hostname` — this operator's own store, outside every checkout. `TS_AUTHKEY` overrides the first.

## Check

### kakt verify

Polls the invariants a cluster must satisfy before it serves — nodes Ready, secret stores valid, secrets synced, Applications Synced and Healthy, pods Running — until they all hold or the budget elapses. It reports which invariant is outstanding and what it is waiting on, so a cluster that is still settling reads differently from one that is stuck.

```bash
kakt verify --cluster acme-hub --timeout 15m
```

| Flag | Meaning |
| :- | :- |
| `--cluster` | The cluster to verify. Its kubeconfig comes from the box's escrow, read with your own `kakt login` session |
| `--kubeconfig` | Where to reach it, when that is not where Day-0 put it |
| `--timeout` | How long to wait before reporting what is outstanding. Defaults to 15m |

### kakt bundle-version

Prints the platform version this binary carries. It reports the constant the release wrote into the binary; it never derives it. `development` means no version was injected, so platform content comes from a working tree rather than a published bundle.

```bash
kakt bundle-version
```

### kakt proposal preflight

Produces the verdict for a proposed version against the cluster it targets: that the release's declared minimum permits the step, that the version is published where your box pulls from, and that the cluster is reconciling now.

```bash
kakt proposal preflight --candidate <version> --cluster acme-hub
```

A check that cannot run returns unverified rather than passing. `--fail-on-unverified` exits non-zero on that, `--out` writes the markdown verdict to a file and `--json` writes it as JSON. See [Versioning](/versions/overview) for what a version is.

### kakt cluster match-inventory

Lists the machines your management cluster holds for a managed cluster alongside the servers your provider actually has, and classifies every relationship between them. Matched means one server carries that machine's name in the provider's own labels.

```bash
kakt cluster match-inventory --cluster acme-02
```

Read-only. It changes nothing in either the cluster or the provider, and unresolved rows stay unresolved — nothing here adopts or remediates. `--hcloud-token` is taken explicitly, or from `HCLOUD_TOKEN`, rather than read from the cluster, because during a reconstruction the cluster's own copy is itself restored state.

## Repair

### kakt reseed

Re-renders the Day-0 seed from the current CLI and applies it. Use it after a seed parameter changes, which otherwise reaches only newly created clusters.

```bash
kakt reseed --kubeconfig acme-hub.kubeconfig
```

The management secret scope, provider and topology come from the cluster's existing seed, so a reseed cannot change which cluster the seed describes. The version is left as the cluster records it; `--bundle-version` moves it deliberately, and the move is printed against the version it replaces.

### kakt cluster restore-pki

Writes a managed cluster's escrowed trust roots into a replacement management cluster, so it can issue node certificates for a cluster that is already running.

```bash
kakt cluster restore-pki --box acme-hub --cluster acme-02 --kubeconfig new-hub.kubeconfig
```

For reconstruction, not for provisioning: a new managed cluster gets new trust roots on the ordinary declarative path. It refuses to run unless cluster lifecycle is paused on that cluster, fails closed when the escrow holds nothing, and fails explicitly when a live value disagrees with the escrow rather than overwriting either. Safe to re-run, and it reports fingerprints only.

## Destroy

### kakt teardown

Deletes a box: the management cluster, the managed clusters it holds, and the cloud infrastructure behind them. It reads the managed clusters from the management cluster, so one run takes the box.

```bash
kakt login
kakt teardown --name acme-hub --gitops-dir . --confirm
```

Access is resolved before anything is destroyed: the box's declaration names its escrow, and the escrowed kubeconfig and provider credential are read with your identity ([Signing in](/cli/signing-in)). Nothing is read from your disk, so the machine that created the box has no special standing.

Then the provider is asked what the box actually has, and you confirm against **that**, not against a name:

```
Target
  management cluster  acme-hub
  workload clusters   acme-stg-01
  state               infrastructure present, Kubernetes reachable

To delete (3)
  server           acme-hub-control-plane-x7k      id=62418891   caph-cluster-acme-hub=owned
  ...
Excluded (2) -- not deleted
  server           acme-prod-01-md-9fj             id=62418744   owned by acme-prod-01, which this operation does not target
  volume           pvc-5c1e                        id=20114      shared with other clusters (caph-cluster-acme-hub=shared)
```

A resource is deleted only when it carries `caph-cluster-<cluster>: owned` for a cluster in that target set — the ownership label CAPH writes. Resources marked `shared`, resources with no ownership label, and resources belonging to a cluster you did not name are listed and left alone. Nothing is selected by name, prefix or substring, which is why a box whose clusters share a prefix (`acme-hub`, `acme-stg-01`) cannot lose the wrong one.

### The management cluster goes last

A management cluster is not torn down while a cluster it manages is still there. The command refuses, names what it found and where it learned of it, and deletes nothing:

```
teardown failed: the management cluster goes last

acme-hub manages a cluster that is still there:

  acme-stg-01                      the management cluster's own CAPI inventory

A management cluster is not torn down while a cluster it manages is running.
It holds that cluster's CAPI objects and the only controller that can deprovision
its load balancers, so once this box is gone the platform cannot delete the cluster
at all: its servers keep running, and keep billing, with nothing left that knows
they exist.
```

Remove each managed cluster first with [`kakt tenant remove-cluster`](#kakt-tenant-remove-cluster), then tear the box down. Or, when the whole box is going, name them on the teardown itself:

```bash
kakt teardown --name acme-hub --gitops-dir . --confirm \
  --destroy-managed acme-stg-01
```

The management cluster then does the deleting: the box's root Application is removed so nothing recreates what goes next, each named cluster's Applications are deleted and waited on — which is what destroys the cluster, with its load balancers deprovisioned by the controller that owns them — and only then is the management cluster itself touched. A cluster that does not finish deleting stops the run, with the management cluster intact, because it is the only thing that can still complete it.

That leaves the clusters' declarations in the repository, which is correct only because the repository is going too. To keep the box, use `remove-cluster`.

The check is made twice, from different evidence, because each source is blind to something the other sees:

- **The management cluster's own CAPI inventory**, asked before anything is destroyed. Authoritative while the cluster answers, and the gate runs before the drain and the finalizer strip, both of which are already irreversible.
- **The provider's inventory**, for every cluster the box declares in `registry/clusters/` or you name with `--managed-cluster`. This catches a cluster whose CAPI objects were deleted while its servers survived — a half-finished removal — and it is the only check available for a box whose API is gone. A cluster the provider says owns nothing is gone for this purpose: no resource in the project carries its ownership label.

A management-cluster teardown no longer cascades into the clusters it manages. It used to read the hub's cluster list and sweep them into the same run, which destroyed clusters nobody named on the command line and, when half the sweep failed, left the remainder with no management cluster to delete them from.

### Two modes, chosen explicitly

**Normal.** The Kubernetes API is reachable: the cluster's own cleanup runs first — load balancers deprovisioned by the controller that owns them, finalizers stripped, DNS ownership read — and then the provider resources go.

**Infrastructure-only.** The API cannot be reached, so you ask for the recovery path by name:

```bash
kakt teardown --name acme-hub --gitops-dir . --confirm \
  --infrastructure-only acme-hub,acme-stg-01
```

It deletes only positively owned provider resources and reports everything the cluster would have done as outstanding. A missing kubeconfig never turns the first mode into the second: without access and without the flag the command refuses, and asking for the flag on a box that *is* reachable is refused too.

The clusters named on the flag are the ones this run destroys, **in order**: each workload cluster first, then the provider is asked again, and the management cluster goes only once nothing in the project carries the others' ownership labels. If anything of theirs survives, the management cluster is left standing on purpose — it is the only thing that could still finish the job — and the run exits non-zero saying so. Naming a workload cluster is the only way one enters a teardown's target set; `--managed-cluster` names a cluster for the ordering check and does not authorize deleting it.

<Note>
If anything could not be done, the command says what and exits non-zero — including a provider deletion that failed. "Teardown completed" means completed.
</Note>

| Flag | Meaning |
| :- | :- |
| `--name` | The management cluster to destroy. Required |
| `--confirm` | Confirm deletion. Required |
| `--gitops-dir` | The box's repository, which declares its escrow and its box id |
| `--destroy-managed` | Also destroy these managed clusters first, through the management cluster, before it is destroyed itself (comma-separated) |
| `--timeout` | How long to wait for each managed cluster's own deletion (default 30m) |
| `--kubeconfig` | Use this kubeconfig instead of the escrowed one, for a box that never finished bootstrapping and so escrowed none. Requires `HCLOUD_TOKEN` |
| `--infrastructure-only` | Destroy the provider infrastructure of a box whose Kubernetes API cannot be reached, naming the clusters to destroy. The workload clusters named are destroyed first and the management cluster last. The cluster's own cleanup is reported as not done |
| `--managed-cluster` | A managed cluster this box declares, repeatable. For when the management cluster can no longer be asked for its list. It feeds the ordering check; it does not authorize deleting that cluster |
| `--dns-only` | Release this box's DNS records and nothing else |
| `--dns-owner`, `--dns-zone` | Which records, and the zone they live in, when the cluster can no longer be read |

<Warning>
This destroys infrastructure in your cloud account and is not reversible.

If it cannot resolve access it stops rather than proceeding: a teardown that cannot read the cluster reports its cleanup as incomplete, and one with no provider credential fails instead of deleting nothing and claiming success.
</Warning>

<Note>
`--infrastructure-only` and `--managed-cluster` exist for a box that is already partly gone. The managed-cluster list normally comes from the management cluster; once that cluster is unreachable it answers nothing, and its clusters survive a teardown that was meant to take them. So you name them, and each one's resources are still matched by its own ownership label rather than by anything about its name. `--dns-only` covers the matching case for DNS: records whose owner no longer exists are ignored rather than reclaimed, so a hostname resolves to a decommissioned address until someone releases it.

`--tenant` is gone. It named the box's prefix so servers could be matched by it, and because a box's clusters share that prefix by construction, a management-cluster teardown would sweep its workload clusters' servers too. Passing it now errors rather than quietly changing what gets deleted.
</Note>

### kakt tenant remove-cluster

Deletes a managed cluster's declaration. **The commit is the removal.** For the whole task, see [Remove a managed cluster](/guides/clusters/remove-a-managed-cluster).

```bash
kakt tenant remove-cluster --mgmt-cluster acme-hub --name acme-02
git add -A registry && git commit -m "Destroy acme-02" && git push
```

A managed cluster exists because `registry/clusters/<name>/infrastructure/spokepool.yaml` exists: the management cluster generates that cluster's Applications from the claim file. So once the commit reaches the branch the management cluster reconciles, the Applications stop being generated, the infrastructure one is deleted with Argo CD's resources-finalizer, the claim goes with it, and Crossplane and Cluster API unwind the cluster.

The command lists the environment's applications — what stops running on this cluster — and refuses only while the management cluster's own `burstSpokePool` names it. Applications are never a precondition: they name no cluster, their definitions belong to the environment, and they keep running on every other cluster serving it. Then it deletes the declaration from your working tree and destroys nothing, because nothing is committed yet.

| Flag | Meaning |
| :- | :- |
| `--mgmt-cluster` | The management cluster that created it. Required |
| `--name` | The managed cluster to remove. Required |
| `--gitops-dir` | Your GitOps repository. Defaults to the current directory |

<Warning>
The commit destroys the cluster and its databases. Its secrets and backups stay, and its name is never reused.
</Warning>

<Note>
`--destroy` is gone, with `--kubeconfig` and `--timeout`. It existed because the per-cluster Applications used to be flat files in the management cluster's directory, which is applied by a root that does not prune — so removing the files left both Applications, and the cluster, running, and a second credentialled step had to delete the objects. The claim file is the declaration now, so there is no window left for that step to close.
</Note>

### kakt tenant cluster-status

Reports what is actually left of a managed cluster. Read-only.

```bash
kakt tenant cluster-status --name acme-02 --mgmt-cluster acme-hub
```

```
cluster  acme-02

Observed
  declaration in git                 absent
  Application acme-02-generated      absent
  Application acme-02-infrastructure deleting
  SpokePool acme-02                  present
  Cluster acme-02                    deleting
  provider resources                 4 owned

state    deleting
  - acme-02-infrastructure is being deleted
  - the claim is no longer declared; the platform is still unwinding the cluster
```

A commit returns at once and a cluster takes minutes to unwind, so this is how you watch it. It reads four sources in increasing order of authority about existence — your working tree, the management cluster's two Applications, the claim and Cluster API object, and your provider's inventory — and prints all of it before the verdict, so the verdict can be checked.

| State | Meaning |
| :- | :- |
| `declared` | The claim is in git and the platform holds the cluster |
| `deleting` | The claim is gone and the platform is still unwinding it |
| `removed` | Nothing holds it, and your provider reports nothing carrying its ownership label |
| `failed` | Needs attention, and the reason says why. Exits non-zero |
| `unknown` | Something could not be read, so nothing is concluded |

`removed` requires the provider to have been asked: **a declaration removed from git is not a destroyed cluster.** The case where nothing on the management cluster holds the cluster any more and its servers are still running is `failed`, not `deleting`, because nothing is left that can finish the job.

### Destroying a managed cluster

There is no command that deletes a managed cluster's servers through your provider's API on its own. With the management cluster running, the cluster exists because a declaration says so and is removed by that declaration leaving — [`kakt tenant remove-cluster`](#kakt-tenant-remove-cluster). With the whole box going, name it on the teardown: `--destroy-managed` while the management cluster still answers, `--infrastructure-only` once it does not.

Deleting the servers behind a running management cluster's back is not a removal: the claim is still reconciled, so the platform rebuilds the cluster on new servers — under a name whose secret path and backup prefix are never reused.
