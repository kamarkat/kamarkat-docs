This is the first thing you do, and all of it happens before any infrastructure exists: you sign in, you create the escrow your box will depend on, and you note the one identity the box will accept as its administrator.

Your box's secret store is encrypted by master keys. The box cannot keep them itself: they are what decrypts it, so they would be unreachable exactly when you need them. The escrow keeps a copy outside the box, in a secret manager you control and Kamarkat does not.

The escrow also holds each cluster's admin kubeconfig, which you use only for [break-glass access](/quickstart/access-your-box#break-glass-access), and the cloud credential your box's infrastructure is built and destroyed with.

You reach it as **yourself**. Step 1 signs you in, and from then on every command that touches the escrow uses your own session rather than a credential copied onto your machine.

<Warning>
Without an escrow, losing the management cluster loses every secret the platform manages for it. You cannot add an escrow afterwards, so creating a box refuses to continue without one.
</Warning>

## Step 1: Sign in and create your escrow account

```bash
kakt login
```

This opens the escrow secret manager in your browser — `https://app.infisical.com` unless you pass `--domain`. Create your account there if you do not have one, or sign in. You do not need to visit the site separately: `kakt login` takes you to it, and hands the session back to the CLI when you are done.

Once you are signed in, Infisical offers an **Open Infisical Dashboard** button if you want to look around. You do not need the dashboard for anything below.

The session is kept in your operating system's credential store, not in a file, and no box ever holds a copy.

```bash
kakt whoami
```

```text
you@acme.example at https://app.infisical.com
  identity      3f9c1b7e-...-a21d
  organization  org_abc123
  session kept in macOS keychain
```

**Keep that `identity` value.** You need it when you [initialize your box](/quickstart/initialize-your-box), which declares it as the box's platform administrator — the one human the box accepts for escrow-backed operations. An address is not used for that, because an address can be changed and re-assigned.

## Step 2: Create the escrow project

```bash
kakt escrow init --name acme-escrow
```

That is the whole step. It runs as you, and it:

- creates the escrow project, **with you as its admin** — because you created it
- creates your organisation's automation identity if it does not have one, configures its authentication, and issues one client secret
- gives that identity access to this project
- writes the four `INFISICAL_ESCROW_*` values to `~/.kamarkat/infisical/`, once for this machine

Nothing to do in the Infisical dashboard, and no roles to choose. The identity gets the organisation role `no-access`, because it performs no organisation action, and the project role `member`, which is what reading and writing secrets and creating folders needs — not `admin`.

The identity it creates for you is an Infisical **machine identity**: an account that belongs to a program rather than a person, authenticating with **Universal Auth** — a client ID and a client secret — instead of a password and a browser. Infisical's own [Machine identities](https://infisical.com/docs/documentation/platform/identities/machine-identities) page describes the mechanism in full; what the platform configures is exactly the part described here, and it is yours afterwards. [Operating the machine identity](/documentation/escrow/platform-administrator#operating-the-machine-identity) covers what that means — what holds its credential, how rotation works, and what the one-per-organisation choice costs.

The client secret is the part to notice: Infisical returns it **once**, at the moment it is issued, and no dashboard and no API can show it again.

<Note>
**One automation identity per organisation, not per box.** A second box reuses it and is added to its own escrow project. Infisical's free plan allows five identities in total, humans and machines together, so an identity per box would exhaust it at the fifth — and the escrow paths are already box-scoped, so a second identity buys no isolation.

A re-run finds the identity, its authentication and its project membership and leaves them as they are. It does issue a client secret each time, because Infisical shows one only at the moment it is created and there is no way to read back the one you have — so a re-run is also how you recover from losing it. Each secret is separate and separately revocable, and your other boxes keep using theirs.
</Note>

<Warning>
**This needs an organisation admin.** An organisation member can create an identity but cannot give it an authentication method or a client secret, so the identity would exist and be unusable. The command refuses with that explanation rather than leaving one behind.

If you are not an admin of your Infisical organisation, have one run this step.
</Warning>

Pass `--client-id` and `--client-secret` if your organisation's policy is that the CLI creates no identities: the project is still created by you, and the identity you name is added to it.

## Step 3: Check what was written

```bash
ls ~/.kamarkat/infisical/
```

```text
INFISICAL_ESCROW_URL        INFISICAL_ESCROW_CLIENT_ID
INFISICAL_ESCROW_PROJECT_ID INFISICAL_ESCROW_CLIENT_SECRET
```

There is nothing to export. The store belongs to you rather than to a checkout, so every command reads it from any directory — `kakt box init` picks these up without flags. Set `KAMARKAT_HOME` if this machine keeps state somewhere other than your home directory, and the environment still wins where it is set, which is how CI supplies the same four values.

**Back up `INFISICAL_ESCROW_CLIENT_SECRET` somewhere outside this machine.** It was issued once and cannot be read back, so the copy in that directory is the only one; losing the directory means issuing a new secret. It is what your box's automation authenticates with — your own access comes from `kakt login`, so you do not need it to operate the box day to day.
