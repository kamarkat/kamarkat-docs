Everything below belongs to you. Kamarkat never receives any of it: the credentials are stored as secrets on your own GitOps repository and used only by your own CI.

## Step 1: Prepare your accounts

| Account | What it is for |
| :- | :- |
| **Cloud account** | Where your clusters run, and what you are billed for. The `hetzner` provider is the default. |
| **Git organization** | Holds your GitOps repository and your application repositories, runs Day-0 in its CI, and hosts your application charts and images in its package registry. |
| **Domain** | Every hostname in your box sits under it. Its DNS zone must be hosted with your cloud provider's DNS service, because the box creates records and proves domain ownership there for its certificates. |
| **Escrow secret manager** | Holds your box's master keys and admin credential outside the box. See [Get started](/quickstart/get-started). |
| **Object storage** (recommended) | Destination for database backups. A production box without it has no backups. |

## Step 2: Install the tools

You need `git`, `kubectl` and the GitHub CLI `gh`, plus the `kakt` CLI.

The `kakt` binary is published with each platform release. Use the version you want your box to start on:

```bash
export KAKT_VERSION=<version>
curl -fsSL -o kakt \
  "https://github.com/kamarkat/kamarkat/releases/download/v${KAKT_VERSION}/kakt-linux-amd64"
chmod +x kakt && sudo mv kakt /usr/local/bin/
kakt bundle-version
```

`kakt bundle-version` prints the platform version the binary carries.

You sign in with it on the next page: `kakt login` opens your escrow secret manager in the browser, where you create the account if you do not have one. It is how every command that reaches an escrow authenticates, and the only credential you keep on your own machine.

<Note>
The example downloads `kakt-linux-amd64`. Each release also publishes `kakt-linux-arm64`, `kakt-darwin-amd64` and `kakt-darwin-arm64`: use the one for your machine. To build from source instead: `go install github.com/kamarkat/kamarkat/cmd/kakt@v<version>`.
</Note>

## Step 3: Gather your credentials

Day-0 runs under secrets stored on your GitOps repository. [`kakt box init`](/quickstart/create-your-box) collects them for you — one step each, opening the page that issues the credential and waiting while you create it — and stores them on the repository it creates. So this is what to expect to be asked for, not a list to assemble in advance.

One exception is worth doing first, because it is needed before the repository exists.

### Before you create the box

| Credential | What it is |
| :- | :- |
| `GITHUB_ORG_SETUP_TOKEN` | **Yours, not the box's.** The credential that creates the repository in your git organization, so it is needed before any repository secret can be set. Either an App installation token, which is preferred because the access stays yours to revoke, or a personal access token with the `repo` **and `workflow`** scopes — supply whichever you have and nothing else changes. `workflow` is not implied by `repo`, and your box's repository carries the workflow that bootstraps it, so a token without it creates the repository and is then refused by the push. `kakt box init` asks for it and keeps it on this machine, so you supply it once per machine rather than once per box. |

### Required

| Secret | What it is |
| :- | :- |
| `HCLOUD_TOKEN` | Your cloud API token, read and write. Your clusters are created with it. It is enrolled into your box's escrow on the first bootstrap and read from there afterwards, so you supply it once. |
| `GITOPS_REPO_WRITE_TOKEN` | Write access to your git organization's repositories, plus that organization's **Secrets: write** permission. Day-0 commits what it generates with it, and your application builds inherit it. |
| `INFISICAL_ESCROW_URL`, `INFISICAL_ESCROW_PROJECT_ID`, `INFISICAL_ESCROW_CLIENT_ID`, `INFISICAL_ESCROW_CLIENT_SECRET` | Your escrow. You create these on the [next page](/quickstart/get-started) — nothing to gather in advance. Scaffolding refuses without them, because an escrow cannot be added after the fact. |

### Required for what your box runs

Scaffolding refuses if a capability your box selects has no credential.

| Secret | What it is for |
| :- | :- |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | Backups of the platform database. |
| `GHCR_USERNAME`, `GHCR_TOKEN` | Pulling your own private images. The platform's images are public. |

### Supplied for you

You are not asked for these, and you do not need to invent them.

| Secret | Where it comes from |
| :- | :- |
| `INFISICAL_ADMIN_EMAIL` | The account you signed in with. Your box runs its own Infisical, separate from your escrow, and this is the address its administrator account is created for. Set `INFISICAL_ADMIN_EMAIL` only to name somebody else. |
| `INFISICAL_ADMIN_PASSWORD` | Generated, written to your escrow, and set on your repository in one step. It is recovered from the escrow rather than from memory, which is also what lets a second run re-enter an Infisical the first one created. |

### Optional

| Secret | What it is for |
| :- | :- |
| `GRAFANA_IRM_ALERTMANAGER_URL`, `GRAFANA_IRM_HEARTBEAT_URL` | Where critical and warning alerts page you, and a heartbeat that pages when the management cluster stops reporting. Metrics, logs and dashboards run in the box without them. |
| `ZITADEL_SMTP_URL` | Outbound mail for identity messages and alert email. |
| `TS_AUTHKEY` | Only if the box accepts nodes on your own premises, which join over your tailnet. |

<Tip>
Export each value as an environment variable of the same name in the shell you will run `kakt box init` in. It reads them from there and stores them on your repository. It never prints or keeps them.
</Tip>
