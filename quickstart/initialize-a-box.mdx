A box outlives every cluster in it, so the box is what you initialize and a cluster is a declaration you add to it afterwards. This page is the first half: the box, with no clusters.

```bash
kakt box init --tenant acme --git-org acme-inc --domain acme.example --region fsn1
```

| Argument | Example | What it is |
| :- | :- | :- |
| `--tenant` | `acme` | Your tenant identifier. It names the box and its repository, and it is the one value you choose. Required |
| `--git-org` | `acme-inc` | The **git organization** the repository is created in. Optional — see below |
| `--domain` | `acme.example` | The domain every hostname in your box sits under. Its DNS zone must be hosted with your cloud provider |
| `--region` | `fsn1` | Where the box's clusters are created. Defaults to your provider's; `--help` lists what else can be overridden |

`--tenant` and `--git-org` are different things and are not renamed to match each
other: `acme` is who the box belongs to, `acme-inc` is where its repository
lives.

`--git-org` is optional: leave it out and the command reads your git organization from the platform credential, which reaches exactly one in the ordinary case. It refuses and lists them when there are several, rather than choosing.

`kakt box init` initializes the box: it creates the box's repository in your git organization and renders it from the platform template, with **no clusters**. It writes only the facts unique to you: your tenant, that git organization, your domain, your region, and the identity it mints for the box. This happens once; every change after it is a commit or a pull request.

The box names itself. One timestamp, taken when it is initialized, gives the box id, the repository and the name its first management cluster will take — `acme-1794447136`, `acme-gitops-1794447136`, `acme-mgmt-1794447136` — so one tenant can hold more than one box without the two colliding. The full contract is in [`kakt box init`](/cli/boxes-and-clusters#kakt-box-init); you do not choose or type any of the three.

## Step 1: What the box is built with

Before anything is created, the command shows you every credential your box needs and asks for the ones it does not have. Each one gets a numbered step: what it is for, the page that issues it, a browser opened on that page, and a prompt that waits while you create it.

```text

What this box is built with. Present values are left alone.
  ✓ GITHUB_ORG_SETUP_TOKEN         present    yours, creates the repository in the tenant's organisation
  ✓ HCLOUD_TOKEN                   present    creates this box's clusters, in your own cloud account

acme-inc/acme-gitops-1794447136 is a box, with no clusters.

  box id             acme-1794447136
  repository         acme-inc/acme-gitops-1794447136
  management cluster acme-mgmt-1794447136   (declared next, not yet created)
  checkout           acme-gitops-1794447136

registry/box.yaml records all three. Next, declare the management cluster:

  cd acme-gitops-1794447136
  kakt tenant add-management

Then commit and push it, and dispatch the repository's bootstrap-cluster
workflow with that cluster name. Day-0 builds it from there.

If this run stops before it finishes, continue it with:

  kakt box init --resume acme-gitops-1794447136
```

Nothing is echoed as you type it, and each value is written with mode `0600`. The last three are destinations rather than credentials — where this box sends its alerts and its mail — and you can press enter to skip one; the box then runs without that capability and says so.

**Nothing is initialized until the set is complete.** A run that stops leaves what you have already given staged under `~/.kamarkat/`, and re-running asks only for what is still missing. Re-running is the normal way to use this command.

If a run stops *after* the box is initialized — the push failed, a secret did not land — continue that same box rather than starting another:

```bash
kakt box init --resume ./acme-gitops-1794447136
```

<Note>
Nothing secret is invented or remembered by hand. Your box's secret store gets its seal key when the management cluster is declared, and it is written to your escrow. Its root certificate authority and the PGP key its recovery key is encrypted to were placed in your administrator-only custody project by `kakt escrow init`.
</Note>

## Step 2: The box

Once the set is complete, the same run initializes the box:

```text
[box] platform administrator: you@acme.example (6e1f…)
[box] rendered acme-gitops-1794447136 into acme-gitops-1794447136
[box] authenticating as the platform (personal access token)
[box] created acme-inc/acme-gitops-1794447136
[box] pushed to https://github.com/acme-inc/acme-gitops-1794447136
[box] ✓ escrowed this box's hetzner credential and bound acme-1794447136 to its escrow
…
acme-inc/acme-gitops-1794447136 is a box, with no clusters.

  box id             acme-1794447136
  repository         acme-inc/acme-gitops-1794447136
  management cluster acme-mgmt-1794447136   (declared next, not yet created)
  checkout           acme-gitops-1794447136
```

Most `✓` lines are a **GitHub Actions secret set on the new repository** — `Settings › Secrets and variables › Actions`, or `gh secret list --repo <repository>`. That is where your box is built from: the workflow that creates a management cluster runs in this repository, on your runners, under these secrets, and the platform keeps no copy of any of them. They are not consumed by Day-0 and then spent — a replacement management cluster reads the same secrets later. See [Where the secrets live](/features/admin/git-connection#where-the-secrets-live) for who reads which, and when.

**Your cloud credential is the exception.** It goes to your escrow, not to the repository, and the line that reports it says so. It is the credential that creates *and destroys* this box's infrastructure, so every later command — a bootstrap, a teardown, an inventory — reads it from the escrow and from nowhere else. A token that happened to be set in an environment would authenticate perfectly and answer about a different cloud project: an inventory that comes back empty, a teardown that deletes nothing and reports success. There is no `HCLOUD_TOKEN` secret on your repository, and nothing reads one.

That same write **binds your box to its escrow**: it is the box's first privileged write, so it records, inside the escrow, that this escrow is the one your box belongs to. Afterwards a project nobody established is not treated as your escrow, and a declaration edited without a deliberate rebind is refused instead of followed. [`kakt escrow verify`](/cli/escrow-and-encryption#kakt-escrow-verify) reports both.

<Note>
**Keep the box id.** Every escrow command takes it, and it is minted rather than chosen. `registry/box.yaml` records all three names, so any command run inside the checkout reads them — you need the id by hand only for break-glass access from somewhere else.
</Note>

| Flag | Meaning |
| :- | :- |
| `--tenant` | Your tenant identifier, lower-case. It names the repository and your box. |
| `--git-org` | The git organization the repository is created in. Optional when your platform credential reaches exactly one. |
| `--domain` | Your base domain. |
| `--platform-admin` | The one human this box accepts for escrow-backed operations. Defaults to the signed-in session; pass it only to name somebody else. |
| `--subdomain` | Optional. A DNS label every hostname sits under; empty publishes on the apex. |
| `--provider` | `hetzner` (default), or `hybrid` for nodes on your own machines. |
| `--region` | The cloud region your clusters run in. |
| `--workers` | Cloud worker nodes a cluster of this box starts with. Defaults to 2. |
| `--bundle-version` | The platform version the box starts on. A released CLI defaults to the version it carries; an unreleased build refuses rather than guess. |
| `--dry-run` | Render locally and initialize nothing, which is how to see what you will receive. |
| `--no-prompt` | Never ask: every credential comes from the environment or `~/.kamarkat/`. For automation. |
| `--out` | The checkout to leave behind. Defaults to `./<repository>`. It must be empty or absent — a box is initialized into an empty directory, so running this inside an existing checkout is refused rather than mixing a box into it. |

Pass `--escrow-url`, `--escrow-project-id`, `--escrow-client-id` and `--escrow-client-secret` only to use an escrow this machine did not create, or the credential flags to initialize a box whose secrets are not staged on this machine.

## What is in your repository

```text
acme-gitops-1794447136/
├── registry/box.yaml              what this box IS: its three names, domain, escrow, and the defaults its clusters start from
├── registry/clusters/<cluster>/   one directory per cluster: bundle.yaml (version), values.yaml (yours)
├── environments/<env>/<app>/      one directory per application, added in "Run your first app"
└── templates/                     what you copy to add a cluster, an app or a workload
```

Two workflows come with it. **Bundle pre-flight** judges an upgrade proposal against the cluster it targets. **Cluster removal** reviews a commit that removes a managed cluster's declaration — which is what destroys that cluster — so the branch your management cluster reconciles should require review and that check.

The platform version in `bundle.yaml` changes only through upgrade proposals. Its `repoURL` names the registry the platform's charts are pulled from, and changes if that registry moves. `values.yaml` holds only what you change from the defaults.
