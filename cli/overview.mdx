> `kakt` is the one tool you run against your box. It scaffolds your GitOps repository, creates your management cluster, supplies your applications' secrets, and reaches your escrow when nothing else can.

## What it is

Every command runs under your own credentials, from your machine or your own CI. The CLI holds no state of its own: it reads your GitOps repository and your clusters, and writes to them. Nothing it does reaches Kamarkat.

The binary carries the platform version it was built for. A box starts on the version the CLI that scaffolded it carried, and moves only through an upgrade proposal you accept.

## Install it

```bash
export KAKT_VERSION=<version>
curl -fsSL -o kakt \
  "https://github.com/kamarkat/kamarkat/releases/download/v${KAKT_VERSION}/kakt-linux-amd64"
chmod +x kakt && sudo mv kakt /usr/local/bin/
kakt bundle-version
```

## Every command

<Note>
Run `kakt <command> --help` for the complete flag set of any command. This page lists what exists; the pages below document the flags that change what a command does.
</Note>

### Sign in

| Command | What it does |
| :- | :- |
| `kakt login` | Authenticate to the Infisical your boxes escrow to, as yourself |
| `kakt whoami` | Show which identity `kakt` would use to reach a hub, and where the session is kept |
| `kakt logout` | Remove this machine's stored session |

A command that reaches a management cluster — `kakt kubeconfig`, `kakt teardown` — does not read a kubeconfig off your disk. The box's repository declares which escrow holds its credentials, and `kakt` reads the escrowed kubeconfig with **your** identity, uses it, and discards it. So any authorized workstation can operate the box, and none of them needs a copy of anything.

Automation does not log in. Set the machine identity instead, which every command prefers when it is present: `INFISICAL_ESCROW_URL`, `INFISICAL_ESCROW_PROJECT_ID`, `INFISICAL_ESCROW_CLIENT_ID`, `INFISICAL_ESCROW_CLIENT_SECRET`.

<Note>
Reading the escrowed kubeconfig gives you **cluster-admin**, because that is what the credential is. Being logged in is an authorization boundary at the credential, not per-person RBAC inside the cluster — day-to-day access is OIDC through your box's own identity provider, where you authenticate as yourself to the API server.
</Note>

### Create and declare

| Command | What it does |
| :- | :- |
| `kakt tenant scaffold` | Create your GitOps repository and start Day-0 |
| `kakt tenant add-cluster` | Declare an additional managed cluster |
| `kakt tenant set-gitops-token` | Publish the credential your application builds use |
| `kakt bootstrap-mgmt` | Create the management cluster, as one step rather than a whole box |
| `kakt init-secrets` | Generate the bootstrap secrets the secret store starts from |
| `kakt configure-github-access` | Give the GitOps engine access to your repositories |
| `kakt configure-tailscale` | Supply the auth key nodes on your own premises join with |

<Warning>
`kakt --help` also lists `configure-eso`. It is deprecated and does not belong in any procedure: running it replaces the machine identity your box authenticates with and stops every platform operator. `kakt init-secrets` creates that identity, and nothing else should write it.
</Warning>

### Destroy

| Command | What it does |
| :- | :- |
| `kakt tenant remove-cluster` | Remove a managed cluster: its declaration, then, with `--destroy`, the cluster |
| `kakt spoke teardown` | Destroy managed clusters through your provider's API, when the management cluster is gone |
| `kakt teardown` | Destroy a whole box: its management cluster, the managed clusters it holds, and their infrastructure |

<Warning>
These delete infrastructure in your cloud account and are not reversible. Each requires an explicit flag: `--destroy`, `--force` or `--confirm`.
</Warning>

`kakt teardown` takes the whole box: it reads the managed clusters from the management cluster and removes them with it. `kakt tenant remove-cluster` takes one managed cluster down while the box runs. `kakt spoke teardown` is only for when the management cluster is already gone and its clusters would otherwise be left running.

Removing an **application** is not a command. Delete its directory under `environments/<env>/<app>/`, regenerate the hostname aggregate with `kakt app hosts aggregate`, and commit — your management cluster removes what the declaration no longer asks for.

## Conventions these commands share

### Secrets are never arguments

No command takes a secret value as a flag. Values arrive on a prompt with echo disabled, or on stdin so a password manager can pipe into them. A secret passed as an argument sits in your shell history and in the process table for anyone on the machine.

### Four flags recur

| Flag | What it names |
| :- | :- |
| `--cluster` | The cluster the command acts on |
| `--box` | The logical box the escrow is keyed by. It is pinned at scaffold and never changes, so escrow artefacts stay findable across a rebuild |
| `--kubeconfig` | Where to reach the cluster, when it is not where Day-0 put it |
| `--repo` | The root of your GitOps repository, which defaults to the current directory |

Commands that read your applications take `--repo`, and read the tenant and the cluster from each application's own `values.yaml` rather than asking you to retype them.

### Dry runs change nothing

`--dry-run` reports what a command would do and writes nothing. Where a command is destructive, it also requires `--confirm`.

### Fingerprints, not values

Commands that inspect secret material print fingerprints. A fingerprint is enough to compare one store against another and useless to anyone who obtains it.
