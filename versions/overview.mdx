> A Kamarkat version is a set of components tested together and published as one release. Your clusters run a version, never a mix of component versions.

## What it is

A release publishes one semantic version, such as `0.1.15`. The same string names every part of the release.

| Part of a release | Where it is published |
| :- | :- |
| **Bundle chart** | `oci://ghcr.io/kamarkat/charts/environment-manager` |
| **`kakt` CLI** | Release assets `kakt-darwin-amd64`, `kakt-darwin-arm64`, `kakt-linux-amd64` and `kakt-linux-arm64` |
| **Release notes** | The release page for tag `v<version>` on `kamarkat/kamarkat` |
| **Third-party inputs** | Release asset `third-party-charts-<version>.tar.gz`: the upstream charts the bundle was built from |
| **Component inventory** | `components.json` inside the bundle chart, also attached to the release |

A published version is immutable. It is never re-published, re-pointed or deleted. A defective version is superseded by a newer one.

## How it works

### What a version carries

The bundle chart renders the platform's cluster machinery, the capabilities you select in a cluster's values, and the infrastructure your applications rest on: namespaces, access rules, secret bindings, gateways and TLS. Selecting a capability is a value, not a version, so adopting a capability and upgrading a version are separate changes.

### Where a cluster records its version

Each cluster pins its own version in your GitOps repository, at `registry/clusters/<cluster>/bundle.yaml`:

```yaml
sources:
  - repoURL: ghcr.io/kamarkat/charts
    chart: environment-manager
    targetRevision: 0.1.15
    helm:
      parameters:
        - name: bundleVersion
          value: "0.1.15"
```

`targetRevision` and `bundleVersion` carry the same version and change together. Your settings live beside this file, in `values.yaml`.

### Where the first version comes from

The `kakt` CLI carries its version. `kakt tenant scaffold` pins your management cluster to it unless you pass `--bundle-version`. Check what a binary carries with:

```bash
kakt bundle-version
```

A binary that prints `development` was built without a release version.

## What you need to know

### Releases and prereleases

A prerelease such as `0.1.16-rc.1` is built and published through the same path as a release. It is a distinct version, so publishing it does not use up the release number.

### Gaps in version numbers

A release that publishes anything uses up its version, even if it fails part-way. The next attempt takes the next number.

### Supported environments and providers

The bundle chart declares which combinations of environment and provider it supports. Any other combination is refused when the chart renders.

| Environment | `hetzner` | `hybrid` |
| :- | :- | :- |
| `dev` | Supported | Supported |
| `stg` | Supported | Not supported |
| `prod` | Supported | Not supported |

### Components move only with the bundle

No component is upgraded on its own. A new version is published with the new set, and that version is what a cluster moves to.

## Frequently asked questions

<AccordionGroup>
  <Accordion title="Can I upgrade a single component?">
    No. Components move only as part of a new version.
  </Accordion>
  <Accordion title="Do all my clusters have to run the same version?">
    No. Each cluster pins its own version in its own `bundle.yaml`.
  </Accordion>
  <Accordion title="Where do I see what a version installs?">
    Under **Releases** in this tab. Each version lists every component it installs, by cluster and node role, and what changed from the version before it.
  </Accordion>
</AccordionGroup>
