# Kamarkat Documentation Writing Style

These pages document Kamarkat. The goal is prose that is direct and informative — not too sparse, not over-explained. Every sentence earns its place.

## Tone and voice

- Second person throughout: "you", "your box", "your team".
- Active voice. Avoid passive constructions ("the cluster is provisioned" → "your control plane provisions the cluster").
- Present tense. State what things do, not what they "will" do.
- Confident but not promotional. State facts about the platform; let the capability speak for itself.
- No filler phrases: "easily", "seamlessly", "powerful", "robust", "cutting-edge", "leverage".

## Terminology rules

These are hard constraints — never deviate.

| Avoid | Use instead |
| :- | :- |
| hub | management cluster |
| spoke | managed cluster |
| fleet | application (or app) |
| organization, for anything the platform owns | **tenant** — see the rule below |
| tenant repository | GitOps repository |
| organization provisioning | tenant provisioning |
| platform tools (alone) | capabilities, introduced as "the platform tools your apps need" |
| catalog, register an app | none: every capability ships in the bundle, and an app exists because its declaration is committed |
| catalogue, catalog (of components) | capability, bundle |
| Kamarkat deploys / applies / pushes to your cluster | Kamarkat publishes a version; your control plane applies it |
| Kamarkat manages / operates your box | Kamarkat delivers the platform into your box |
| upgrade (as something Kamarkat does) | upgrade proposal you accept |
| SaaS, hosted platform | delivered into your box |
| internal component names (`hub-operator`, `kube-sbt`, `mcp-server`) | the capability they provide (platform operator, tenant provisioning, control-plane API) |

### Tenant, not organization

**Tenant** is the platform's word for the owner of a box: its clusters, its
applications, its costs and its isolation boundary. Use it in prose, not only in
`tenantId` and `--tenant`.

**Organization** means one thing and nothing else: the identity provider's own
container for users, projects and clients. A tenant is bound to one. That is the only
place the word may carry the platform's meaning.

The one other legitimate use is **"git organization"**, which names the reader's entity
in their git provider — what `--org` sets, and where their repositories, runners and
package registry live. Always qualify it with "git". A bare "your organization" is
forbidden precisely because it has meant both the tenant and the git organization,
sometimes in the same sentence.

For plain English about companies, write "teams" or name them: "built for teams without
a platform team".

### No vendor names

Name the capability, never the third-party project behind it: "the GitOps engine", "the identity provider", "the secret store", "the database", "observability". The exception is a literal value the reader must type or set — a secret name, a URL, a CLI tool — where the vendor name is part of the value.

Two exceptions. A capability page's **Built on** section names the open-source projects behind that capability; it is the only prose place a project is named. The generated release pages list every component by name, because they are an inventory.

### One home per fact

Never state a fact in two places; link to its home instead.

| Fact | Its only home |
| :- | :- |
| What a capability gives you, and the projects it is built on | Its page under **Features › Capabilities** |
| Which capabilities exist, machinery or selectable, and their values key | The table in **Capabilities › Overview** |
| Component versions, licences, images, node placement | **Versions › Releases**, generated by `scripts/sync-releases.py` |
| How the clusters, boundaries and connections fit together | **Introduction › Architecture** |
| How you declare, promote and deploy your applications | **Features › Workloads** |

### No internal references

Customer documentation never cites ADR numbers, internal file paths of the platform repository, ticket ids or design history. Describe only the current design, never what it replaced.

### Only the CLI, never a script

Every procedure in these docs is a `soloz` command. Never document a script that ships
in the GitOps repository, and never put one in a command block, a repository tree or a
prerequisite — `./scripts/anything.sh` must not appear on a page.

The reason is that two interfaces mean two contracts. A script in a tenant's repository
is a copy: it ages with the repository it was rendered into, while the CLI the reader
installs carries the platform version. Documenting both leaves a reader with two answers
and no way to tell which is current.

`git`, `gh` and `kubectl` are fine — they are tools the reader already installed, named
in the prerequisites. The rule is about scripts the platform ships, not about other CLIs.

When a procedure can only be done with a script, that is a gap in the CLI. Report it;
do not document your way around it.

## Page anatomy

### Feature pages

Every page under **Features** follows this structure — in this order. Do not invent new sections or reorder them.

```
---
title: "Page Title"
description: "One sentence for the page header."
---

> One or two sentences. What the capability does and why it matters. Plain statement — no marketing copy.

## What it is

3–5 sentences. Explain the concept and how it fits the box.
A table is appropriate here when comparing kinds, modes or owners.

## Getting started   (or: How it works)

Numbered walkthrough with ### sub-steps. Imperative phrasing.

## What you need to know

Operating semantics: ownership, isolation boundaries, what propagates and when, limits.
Use ### sub-headings for distinct concerns.

## Tips

4–6 bullet points. Bold the key action or principle, then one sentence of explanation.

## Frequently asked questions

<AccordionGroup> of 2–6 questions a user would actually ask. 2–4 sentence answers.
```

### Capability pages

Every page under **Features › Capabilities** other than the overview follows this structure:

```
> One sentence: what the capability gives you.

## What it gives you        bullets, each a thing the reader gets
## What you own             only if the reader owns part of it
## How to turn it on        only for a selectable capability: the values key and its default
## Built on                 table: Project | Role in your box | Runs on
                            then one line linking to Versions › Releases for versions
```

Roles come from `component-catalog.yaml` in the platform repository; **Runs on** comes from the latest release inventory. Never write a version number on a capability page.

### CLI reference pages

Pages under **CLI** document the command surface. One page per command family, plus an
overview that indexes every command:

```
> One or two sentences: what this family of commands acts on.

## <Verb>                   group commands by what the reader is doing: Create, Check,
                            Repair, Destroy. Never alphabetically
### soloz <command>         one per command, in the order a reader meets them
                            1-3 sentences, then the command in a fenced bash block,
                            then a flag table where a flag changes what happens
## What you need to know    only where semantics outlive a single command
```

Rules specific to these pages:

- The overview's index must list **every** command the CLI exposes. Walk the built
  binary's help, not the source, and do not omit a command because it is dangerous or
  deprecated — a reader who sees it in `--help` and not here will assume the docs are
  stale. Say what it does and whether to run it.
- Document the flags that change behaviour, not every flag. Point to
  `soloz <command> --help` for the complete set.
- A destructive command gets its own group heading with the word Destroy in it, and a
  `<Warning>`. Never file one under a heading about checking or running.
- Never carry the CLI's help text across verbatim. It cites decision records, platform
  file paths and internal component names, all of which are forbidden here.

### Quickstart pages

Every page under **Quickstart** is a procedure:

- A one-paragraph introduction saying what the page achieves.
- `## Step 1: ...`, `## Step 2: ...` headings, each with the exact command in a fenced `bash` block.
- A flag or field table after the first command that introduces it.
- `<Note>`, `<Warning>` or `<Tip>` only where a reader would otherwise fail.
- A closing `## Next` with one `<Card>` linking to the following page.

Commands and flags must exist in the `soloz` CLI at the documented version. Verify each one against the CLI source before writing it.

## Section heading conventions

Use sentence case for every heading.

| Section | Exact heading text |
| :- | :- |
| Concept | `## What it is` |
| Walkthrough | `## Getting started` or `## How it works` |
| Semantics | `## What you need to know` |
| Best practices | `## Tips` |
| Q&A | `## Frequently asked questions` |
| Procedure step | `## Step N: Verb phrase` |

## Length calibration

| Section | Target length |
| :- | :- |
| Lead blockquote | 1–2 sentences |
| What it is | 3–5 sentences, optionally 1 table |
| Each ### sub-step | 3–6 sentences |
| What you need to know (each sub-section) | 3–6 sentences |
| Tips | 4–6 bullets |
| Each FAQ answer | 2–4 sentences |

Do not pad to fill space. Do not truncate to save space.

## Sentence construction

- One idea per sentence.
- Short sentences for key facts. Slightly longer sentences to explain relationships or sequence.
- Start sentences with the subject, not a clause: "Your control plane reconciles..." not "Once the proposal is merged, your control plane reconciles..."
- When describing a sequence of events, prefer numbered lists or `<Steps>` over long compound sentences.

## What to avoid

- Bullet-dumping where prose would read better.
- Nested bullets more than one level deep.
- Bold text used decoratively. Bold only key terms or actions the reader needs to find quickly.
- Phrases that inflate without adding information: "It is important to note that...", "In order to...", "Please be aware that..."
- Ellipsis or em-dash overuse in body copy.
- Claims the platform does not make. If a design is decided but not yet built, say so rather than describing it as available.

## Product identity — read this before writing anything

This is the most important section. Get this wrong and all the writing will be wrong.

**What Kamarkat is:**
Kamarkat is an open-source platform a startup runs its business on. It delivers a complete platform into a box in the customer's own cloud account, for teams that want a golden path and cannot yet staff a platform team.

**Scope: open source only.** The docs describe the open-source, turnkey platform. Commercial content (support, maintenance commitments, credits, billing, metering, pricing) is out of scope until it is added deliberately; drafts live in `scratch/deferred/`. A customer's own cloud bill is infrastructure cost, not commercial content.

**What Kamarkat is NOT:**
- Not a hosted or managed service — Kamarkat operates no customer infrastructure and holds no customer credential
- Not a platform for platform engineers to customise — it is a tested golden path
- Not responsible for the customer's applications — the customer owns their code, images, data and how they use each capability

**The correct mental model:**
- The **box** is the constant — a management cluster and its managed clusters, in the customer's account
- The **GitOps repository** is the only source of desired state for the box
- Kamarkat **publishes versions**; the customer's own automation proposes them and the customer's control plane applies them
- Kamarkat **provides the capability**; the customer **owns its use**

**Core vocabulary:**
- Use **"box"** for what a customer owns, **"tenant"** for whoever owns it, **"application"** for a product running on it
- Use **"capability"** — not "feature", not "service", not "module" — for what the platform provides
- Use **"propose"** for upgrades, **"reconcile"** for what the control plane does

## Concepts to use accurately

**Box**
A management cluster running the customer's control plane, plus the managed clusters it provisions. It runs in the customer's cloud account under credentials only the customer holds, belongs to one tenant, and keeps running whether or not Kamarkat is reachable.

**Tenant and application**
The tenant owns the box (`tenantId`), and is bound to one organization in the identity provider. An application is a product running on it (`appId`), and the unit of isolation: its own namespace `tenant-<tenantId>-<appId>`, database, identity project, secret path and network policy. Being in the same tenant never grants access; only a declaration does.

**Cell**
A managed cluster's name, chosen by the customer and fixed for life. Applications name the cell they run on. Policy attaches to cells.

**GitOps repository**
`<tenant>-gitops` in the customer's git organization. For each cluster it holds the bundle version and the customer's values; for each application, its declaration and the chart version of each workload.

**Bundle**
The whole platform at one immutable version, published as one artefact and mirrored into infrastructure the customer controls. Upgrades change one version field per cluster.

**Capability**
What the platform provides. Machinery runs on every box; selectable capabilities (database, observability, on-premises capacity) are chosen in the cluster's values. Selecting a capability never makes it the customer's to maintain.

**Day-0**
The one-time creation of the management cluster, run from the customer's own CI. After Day-0 the GitOps repository is the only authority.

**Support Agent**
An open-source agent on every cluster that does nothing until the customer enrols. It sends an allowlisted set of control-plane facts outward, and the customer can preview the exact payload first.

**Escrow**
A secret manager the customer controls, outside the box, holding the box's master keys and each cluster's break-glass admin kubeconfig.

## Diagrams

Architecture diagrams use the `arch-*` classes in `style.css`, written as JSX in the page. Interactive layer stacks use the `BoundaryStack` component in `snippets/`. Every element in a diagram must trace to the platform's decisions or its running configuration — never draw a component or a flow that is assumed.
