> Your [escrow](/features/admin/escrow) is a secret manager you control, outside the box, holding its master keys and each cluster's break-glass admin kubeconfig. These commands create it, report what it actually holds, and use it.

## Conventions

Every command here reads the escrow with the same four values. `kakt escrow init` writes them to this operator's own store, `~/.kamarkat/infisical/` — read from any directory, so nothing is exported on the machine that created the escrow. The environment wins where it is set, which is how CI supplies them:

```bash
export INFISICAL_ESCROW_URL=https://app.infisical.com
export INFISICAL_ESCROW_PROJECT_ID=<project-id>
export INFISICAL_ESCROW_CLIENT_ID=<machine-identity-client-id>
export INFISICAL_ESCROW_CLIENT_SECRET=<machine-identity-client-secret>
```

Where a command takes `--gitops-dir`, it needs none of them: the box's repository names its escrow, and the read is performed with your own [`kakt login`](/cli/signing-in) session.

`--box` names the logical box the escrow is keyed by — the box id `kakt box init` minted, which its repository records in `registry/box.yaml`. `--cluster` names the cluster within it. A box keeps its `--box` value across a rebuild, which is how a replacement management cluster finds the keys the old one escrowed.

These commands report fingerprints and never values.

## Create

### kakt escrow init

Creates the project your boxes escrow to, and the automation identity they authenticate with. Run it after `kakt login`, as an organisation admin.

```bash
kakt escrow init --name acme-escrow
```

| Flag | Meaning |
| :- | :- |
| `--name` | The project name. Required |
| `--url` | The escrow's address. Defaults to `https://app.infisical.com` |
| `--out` | Write the `INFISICAL_ESCROW_*` files here instead of this operator's own store (`~/.kamarkat/infisical`, or `$KAMARKAT_HOME/infisical`) |
| `--client-id`, `--client-secret` | Use an identity you manage yourself instead of the organisation's automation identity. Passed together |
| `--gitops-dir` | A box's repository. If it already declares an escrow, that project is prepared rather than a second one created. Defaults to the working directory |
| `--cluster` | Which management cluster's declaration to read, when the repository holds more than one |

It creates the project **as you**, so you are its admin, then finds or creates your organisation's one automation identity, configures its authentication, issues a client secret for this box, and gives it membership of the project. The `INFISICAL_ESCROW_*` values are written to `--out`, including `INFISICAL_ESCROW_ORG_ID` — the organisation your session belongs to, which a box declares so the administrator it names can be checked inside the organisation that issued them.

Run inside a box's checkout, it also fills that organisation into the box's own declarations — `registry/box.yaml` and each cluster's `values.yaml` — when they record none, and prints the files it changed for you to commit. It corrects only a declaration that already names the escrow project this run authenticated against: one naming another project, or already naming another organisation, is refused rather than claimed, and no project id, address or escrowed material is ever moved.

No roles to choose: the identity gets the organisation role `no-access` and the project role `member`, which is what secret and folder operations need.

<Note>
**One automation identity per organisation.** A second box reuses it and is added to its own project — the free plan allows five identities in total, and the escrow paths are already box-scoped. Re-running finds the identity, its authentication and its membership and leaves them alone; the one thing it always does is issue this box a client secret, because an existing one cannot be read back. Universal Auth holds many per identity, so that neither touches nor invalidates what your other boxes are using, and each is revocable on its own.

It needs an **organisation admin**: a member can create an identity but cannot give it an authentication method, so the command refuses rather than leaving an unusable one behind. [Get started](/quickstart/get-started) walks the whole sequence.
</Note>

### kakt escrow bind-destination

Records this box's escrow coordinates inside that escrow, so a declaration and its escrow can be checked against each other afterwards.

```bash
kakt escrow bind-destination --gitops-dir . --cluster acme-mgmt-1794447136
```

| Flag | Meaning |
| --- | --- |
| `--cluster` | The cluster whose declaration to read. Required |
| `--gitops-dir` | The box's repository. Defaults to the working directory |
| `--rebind` | Replace an existing binding, authorizing a move to the declared coordinates |

Run once per box, before any recovery material is written. A box already bound elsewhere is refused unless you pass `--rebind`, and `--rebind` with nothing bound is refused too — a first binding is the plain form, and the two must stay distinguishable.

<Note>
What the binding does and does not establish, who may reach an escrow, and why no command reads a local provider token are explained once, in [Escrow](/documentation/escrow/overview) — not repeated here. This page is the command surface.
</Note>

## Check

### kakt escrow verify

Reports which artefacts your box cannot be rebuilt without are actually present, by fingerprint — so a missing one is visible before a recovery rather than during one.

```bash
kakt escrow verify --box acme-1794447136 --cluster acme-mgmt-1794447136 --management
kakt escrow verify --box acme-1794447136 --cluster acme-02 --workload
```

Pass `--management` for the management cluster, where every artefact applies, and `--workload` for a managed cluster, where the management-cluster-only artefacts do not.

<Tip>
Run this after Day-0. An escrow cannot be added to a box afterwards, so the one time to find out it is empty is before you need it.
</Tip>

### kakt escrow verify-recovery

Decrypts one value, exactly as the cluster stored it, using the key held in the escrow.

```bash
kakt escrow verify-recovery --box acme-1794447136 --cluster acme-mgmt-1794447136 --from /tmp/probe.bin
```

Presence is not recovery. `escrow verify` reports that a key exists; this reports whether that key is the one your cluster's API server is actually encrypting with. A key that decrypts nothing looks identical to a working one in a presence check, and the difference surfaces during a rebuild — the one moment it cannot be fixed.

`--from` takes a file holding one stored value, obtained on a control-plane node so it never leaves the host. Use a probe Secret you created for this, not a real one: the file is ciphertext, but it is one command from plaintext and there is no reason for it to be a credential. Neither the key nor the decrypted value is printed.

## Use

### kakt kubeconfig

Retrieves a cluster's admin kubeconfig from the escrow.

```bash
kakt login
kakt kubeconfig --cluster acme-mgmt-1794447136 --gitops-dir . --out acme-mgmt-1794447136.kubeconfig
kubectl --kubeconfig acme-mgmt-1794447136.kubeconfig get nodes
```

With `--gitops-dir`, the box's own declaration names its escrow and the read is performed with your identity ([Signing in](/cli/signing-in)) — so this works from any authorized workstation. Without it, pass `--box` and the four `INFISICAL_ESCROW_*` values in the environment, which is what automation does.

<Warning>
This is break-glass access. Normal access is through your own identity provider, where each person authenticates as themselves. Use this when that is not available: the identity provider is down, the cluster is broken, or nobody can sign in. The credential is cluster-admin, is not tied to a person, and must never be committed.
</Warning>

The escrow holds one kubeconfig per cluster, so pass the cluster you need. Without `--out` it prints to stdout. `--box` overrides the declaration, which matters for a successor management cluster: it reads its predecessor's artefacts under the box they share, while the declaration names only the current cluster.

### kakt escrow enroll-provider-credential

Puts the cloud credential this box was built with into its escrow, so lifecycle commands can reach the provider from any authorized workstation.

```bash
kakt escrow enroll-provider-credential --gitops-dir . --cluster acme-mgmt-1794447136 < token
```

This is the only place a provider credential is accepted from an operator. Bootstrap does not enrol one: it reads the escrowed copy and refuses to create infrastructure if there is none, because a credential that exists nowhere but the bootstrapping machine cannot destroy what it built. A first enrolment also establishes the box's escrow binding.

The credential arrives on stdin, never an argument, and is never printed back. Re-running with the same credential writes nothing; a *different* one is refused unless you pass `--rotate`, because the escrowed copy may be the only one that reaches infrastructure the box already owns.

<Note>
It is escrowed under the **box**, not the cluster. The credential buys and destroys the box's infrastructure and outlives any cluster in it, so a successor management cluster finds the same one.
</Note>

### kakt escrow migrate-paths

Copies a box's admin kubeconfig and both at-rest encryption key generations onto the per-cluster paths a cluster now has.

```bash
kakt escrow migrate-paths --box acme-1794447136 --cluster acme-mgmt-1794447136 --cluster acme-02
```

It copies and never generates, derives or rotates. It refuses to overwrite a destination holding different bytes, reads every destination back and compares it with its source before reporting an artefact migrated, and leaves the old copies in place.

## Management-state backups

Your box's management state is backed up to object storage you own, encrypted under a customer-supplied key. Both the key and the store credential live in the escrow rather than in the box's own secret store, because they have to work when the management cluster that wrote the backups is gone.

<Note>
These two commands exist and are documented here for completeness. The capability they serve does not deploy yet, so there is nothing to deliver credentials into on a box built today.
</Note>

### kakt escrow enroll-store-credential

Reads the object-store credential for management-state backups from stdin and preserves it in the escrow.

```bash
kakt escrow enroll-store-credential --box acme-1794447136 < credential.ini
```

The credential is yours and is never generated here. It arrives on stdin, so it is not in a command argument, a shell history or a process list, and it is never printed back. Enrolment is one-time: a credential already escrowed is left alone unless `--rotate` is given.

### kakt escrow deliver-backup-credentials

Creates the two Secrets a cluster needs to read its management-state backups: the customer-supplied key the objects are encrypted under, and the store credential that reaches the bucket.

```bash
kakt escrow deliver-backup-credentials --box acme-1794447136 --kubeconfig acme-mgmt-1794447136.kubeconfig
```

Create-only. An identical Secret is accepted as already present; a different one is refused and left alone. A missing escrowed key fails closed and is never replaced by a new one, because a new key cannot decrypt a backup written under the old. `--dry-run` compares and writes nothing.

## At-rest encryption

### kakt encryption enable

Delivers what at-rest encryption of Secrets needs to a cluster that already exists: the Secret its control plane reads its encryption provider configuration from. The key is restored from the escrow when one holds it, and generated otherwise — and a generated key is escrowed before anything is applied.

```bash
kakt encryption enable --box acme-1794447136 --cluster acme-mgmt-1794447136 \
  --apply-class --kubeconfig acme-mgmt-1794447136.kubeconfig
```

| Flag | Meaning |
| :- | :- |
| `--box`, `--cluster` | The box the escrow is keyed by, and whose key this is. Both required |
| `--apply-class` | Also apply the control-plane template. Required for the management cluster, whose template nothing reconciles. Not needed for a managed cluster, where the GitOps engine already carries it |
| `--kubeconfig` | The management cluster, which is where the configuration Secret lives even for a managed cluster |
| `--dry-run` | Say what would be applied, change nothing |
| `--no-plaintext-fallback` | Render the configuration without the plaintext reader |

<Warning>
Run this against the management cluster for any cluster, and run it as the first step of enabling encryption, not the only one. Adopting a new control-plane template replaces each node. `--no-plaintext-fallback` belongs only after every Secret has been rewritten and verified encrypted: any Secret still in plaintext becomes unreadable.
</Warning>

### kakt encryption rotate

Replaces the key Secrets are encrypted with, in two stages, without losing data already written.

```bash
kakt encryption rotate --box acme-1794447136 --cluster acme-mgmt-1794447136 --kubeconfig acme-mgmt-1794447136.kubeconfig
# roll the control plane, rewrite every Secret, verify, then:
kakt encryption rotate --box acme-1794447136 --cluster acme-mgmt-1794447136 --finalize
```

Stage one mints a new key, makes it the write key and retains the current one for reads, so nothing is unreadable at any point. Stage two, with `--finalize`, removes the retained key; it refuses unless the live configuration is actually mid-rotation.

Both stages escrow before they apply, and during a rotation the escrow holds both keys — a cluster that loses its control plane mid-rotation needs both to recover.

<Warning>
Do not run `--finalize` until you have verified that every Secret carries the new key's name. Anything still sealed under the old key becomes unreadable.
</Warning>

The cryptoperiod is 90 days. A key you know has been disclosed is an incident rather than a scheduling question: replace it now, because waiting for the next window keeps a compromised key in force for a quarter.
