> Day-0 runs once. After that, your repository is the only authority.

## What it is

A box comes into existence in two phases.

**Day-0** creates the management cluster. The first cluster cannot reconcile itself into existence, so a command-line tool runs it from outside the box, in your own execution context (for example, a CI workflow in your git organization), against your own cloud account. It establishes trust, identity and configuration, then hands over.

**Day-1 onwards** is declarative. The management cluster reconciles everything from your GitOps repository, including any further clusters. Nothing is triggered and nothing is applied from outside.

## Getting started

### 1. Prepare a git organization and a cloud account

You supply both. Cloud credentials stay in your box and are never given to Kamarkat.

### 2. Scaffold your GitOps repository

`kakt tenant scaffold` creates `<tenant>-gitops` in your git organization. It writes only the facts unique to you: your tenant, that git organization, your domain, region and cluster names.

### 3. Run Day-0

Day-0 bootstraps the management cluster in phases. Each phase records its state, so a run interrupted by a network fault resumes instead of starting over. A phase can be re-run only if it declares that re-running is safe.

Day-0 commits the facts it discovers, such as the control-plane address, to your repository. That is the only write made outside a pull request.

### 4. Declare managed clusters

To add a managed cluster, render the **cluster template** into a new directory in your repository and commit it. Your management cluster provisions it, and keeps it in its desired state from then on.

## What you need to know

### One management cluster, any number of managed clusters

A GitOps repository holds exactly one management cluster and any number of managed clusters, each in a directory named after it.

### You name your managed clusters

A managed cluster's name is chosen by you, written once, and never computed. It is the cluster's `clusterName`, and every per-cluster identity (secret path, backup location, labels, autoscaling targets) derives from it. Applications name no cluster: they are deployed to every cluster serving their environment, so a cluster is swapped out by building a successor that serves the same environment and retiring the old one — no application is edited. See [Replace a managed cluster](/guides/clusters/replace-a-managed-cluster).

### Policy attaches to cells

A cell groups your clusters for policy, and is not a cluster. It holds no compute, pins no version and owns nothing. A cluster may belong to several cells and receives the union of their policy, and a residency policy on a cell is checked against the region of every cluster in it.

### On-premises nodes are a capability

You can add on-premises worker nodes to a cluster at any point in its life. They run workloads and burst capacity, never cluster-machinery state, so replacing one is a capacity operation rather than a recovery.

### Spokes are not workflows

A workflow provisions once and then stops caring; a controller does not. That is why managed clusters are declarations reconciled continuously, not jobs run by CI.


## Built on

| Project | Role in your box | Runs on |
| :- | :- | :- |
| **Cluster API** | Creates, scales and replaces the management cluster and managed clusters | Management cluster |
| **Cluster API provider for Hetzner** | Creates cluster machines, networks and load balancers in your cloud account | Management cluster |
| **Kubernetes** | The control plane each cluster runs, created with kubeadm | Both cluster types |
| **etcd** | The control plane's key-value store | Both cluster types |
| **Kubernetes node tools** | kubelet, kubeadm and kubectl on every node | Both cluster types |
| **containerd and runc** | The container runtime on every node | Both cluster types |
| **Ubuntu** | The node operating system, the provider's stock image | Both cluster types |
| **Hetzner cloud controller manager** | Node lifecycle and load balancers in your cloud account | Management cluster |
| **Hetzner CSI driver** | Block-storage volumes for persistent data | Management cluster |
| **Local path provisioner** | Node-local volumes on clusters without cloud block storage | Management cluster |
| **clusterctl** | Moves cluster management onto the management cluster during Day-0; runs from the kakt CLI, on no cluster | Bootstrap only |

Versions are not listed here: each release lists the exact version of every component it installs, under [Versions](/versions/overview) › **Releases**.

## Frequently asked questions

<AccordionGroup>
  <Accordion title="Do I need to run Day-0 again to add a cluster?">
    No. Day-0 runs once, for the management cluster. Every later cluster is a declaration in your repository.
  </Accordion>
  <Accordion title="Can I rename a managed cluster?">
    No. The name is the cluster's identity, and changing it would destroy what it names. Declare a new cluster instead.
  </Accordion>
</AccordionGroup>
