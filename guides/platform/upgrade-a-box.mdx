> A platform upgrade is a change to one cluster's `bundle.yaml`. Nothing changes until that change is in the branch your management cluster reconciles.

Each cluster pins its platform version in `registry/clusters/<cluster>/bundle.yaml`, on two fields: `targetRevision` and `bundleVersion`. Upgrading a cluster is changing both. Each cluster is upgraded on its own, so you can take a version on `dev` before `prod`.

## Step 1: Read what the version brings

Each version's release notes, on the release for tag `v<version>` on `kamarkat/kamarkat`, list its changes, its security fixes and a **Taking this version** table. Check two of its fields:

- **Minimum version this may be taken from.** The cluster must already run this version or a later one. If it does not, upgrade to an intermediate version first.
- **Predecessor restorable from this version.** Whether going back restores the cluster's previous state: `yes`, `no`, or `unknown` when it was not declared. Treat `unknown` as `no`. See [Roll back a platform version](/guides/platform/roll-back-a-version).

See [Versions](/versions/overview).

## Step 2: Check the cluster can take it

```bash
kakt proposal preflight --candidate <version> --cluster acme-mgmt-1794447136
```

It checks the version's minimum permits the step, that the version is published where your box pulls from, and that the cluster is reconciling now. A check that cannot run reports unverified rather than passing.

## Step 3: Take the version

Run this in your box's checkout:

```bash
kakt release promote --version <version>
```

A cluster records the version in **three** places — `targetRevision` and the
`bundleVersion` value in `bundle.yaml`, and `environmentRevision` in
`values.yaml` — and this rewrites every one of them, then commits and pushes.

That matters more than it looks. `targetRevision` decides which chart is pulled
and `bundleVersion` tells that chart which version it is, so moving one and not
the other leaves the root Application Synced while every child stays on the
previous release. And `environmentRevision` is what your box reports as the
version it runs, so a box that moved the first two and not the third upgrades
while continuing to say it did not.

It refuses rather than half-applying: a version already referenced under
`registry/`, clusters on different versions, a cluster pulling the bundle from
another registry, or the old version still appearing after the rewrite each stop
it before anything is committed. `--dry-run` lists what would change and writes
nothing.

## Step 4: The push upgrades the cluster

Your management cluster reconciles the new version from git. The **Bundle sync**
workflow in your repository drives that convergence and then confirms the
cluster actually reached the version — one run per cluster the commit moved.

It confirms nothing unless you have granted it access. With a
`KUBECONFIG_<cluster>` secret on the repository — the cluster's own name,
upper-cased with hyphens turned into underscores — every upgrade is checked on
the box. Without one the run says so, and you check it yourself:

```bash
kakt verify --cluster acme-mgmt-1794447136
```

To decline a version, change nothing. The cluster stays on the version it pins, and a version you did not take is not a version you have to take later: any version may be taken from any earlier one at or above its declared minimum.
