> A cluster runs a set of components that was tested together before it was deployed, never the newest of each.

## What it is

The **bundle** is the whole platform at one version: every component, every chart version and every default value. It is published as one immutable chart, `environment-manager`, and named by one semantic version.

Your GitOps repository records, for each cluster, the version it runs and the values it runs with:

```text
<tenant>-gitops/
└── registry/clusters/<cluster>/
    ├── bundle.yaml   # the version, changed by upgrade proposals
    └── values.yaml   # yours: only what differs from the defaults
```

None of the bundle's content is copied into your repository. Upgrades write the version and you write the values. The two never touch the same field, so an upgrade never conflicts with your changes.

## How it works

Your control plane pulls the bundle chart at the version in `bundle.yaml` and renders it with your `values.yaml`. Every platform-owned Application on the cluster comes from that one render, so a cluster cannot run two versions at once.

How versions are published, proposed and taken is covered in [Versions](/versions/overview).

## What you need to know

### Defaults belong to the bundle

Your values file holds only what you change. When a default improves in a new version, you get it without editing your values. Any field you overrode stays overridden.

### The bundle includes what your applications rest on

The bundle also renders the infrastructure under your applications: namespaces, access rules, secret bindings, gateways and TLS. A new version updates it on the next reconcile, without any change to your application repositories.

## Tips

- **Keep `values.yaml` small.** Every field you set is a default you stop receiving.
- **Never edit `bundle.yaml` by hand except to pick a version.** Change `targetRevision` and `bundleVersion` together.
